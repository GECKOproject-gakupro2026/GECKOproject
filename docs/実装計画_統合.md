## 2. Context(これから何をなぜ変えるか)

### 解決する2つの実問題

1. **IDLE状態なのにセンサーデータが5Hzで送られてくる**(ToFだけ値が来ない)。
2. **センサーのサンプリングレートが遅く、データが滑らかでない**。

### 原因(コードで確定済み)

**問題1**は仕様通りの実装で、要求と食い違っている。[app_state.c:156-168](../NonSecure/Core/Src/app_state.c#L156-L168):

```c
if (ctx->state == STATE_IDLE) {
  if ((int32_t)(now_ms - ctx->nextTelemetryMs) >= 0) {
    ctx->nextTelemetryMs = now_ms + CFG_IDLE_TELEMETRY_MS;  /* 200ms = 5Hz */
    build_status(&ctx->st);              /* ← IDLEなのに全センサー取得 */
    (void)Comm_SendTelemetry(&ctx->st);  /* ← IDLEなのに送信 */
  }
  ...
}
```

[app_config.h:24-26](../NonSecure/Core/Inc/app_config.h#L24-L26) にも
「*IDLE no longer silences the comm stack — only the slower rate distinguishes it from ACTIVE*」
と明記。これは過去のIDLE再定義(「通信を止めるとIDLE復帰不能になるので止めない」)の名残であり、
現在の要求と矛盾する。**ToFだけ値が来ない**のは `Sensors_Stop()` がIDLE突入時にToFをSLEEPさせ
`s_tofOk=0` にし、[sensors.c:170-177](../NonSecure/Core/Src/sensors.c#L170-L177) が
`tof_ok=0, tof_mm=0` を返すため。「ToF以外は全部動いてIDLEで5Hz送信され続け、ToFだけ止まる」
という観測通りの挙動。

**問題2**は送信レート(50Hz)とセンサー取得レートの乖離。50Hzで送信しても中身は
10Hz/5Hz/2Hzでしか更新されず、同じ値が5〜25回繰り返される。

### 要求する構造(memo.md:78-100)

> **idle**: uartのdmaや各種フラグ、またはwifi BLEからのコマンドを待機している状態。それ以外の動作はしない
> **データ送信**: メモリに保存されているデータを送信する
> **データ取得**: センサーデータを取得する。センサー周期以上のデータ取得を要求する可能性がある。センサー周期はコマンド上で指定できる機構を追加すること
> **データ保存領域**: 構造体を用いてクラス化し、プロジェクト全体で共有する。データ取得では上書きし、データ送信では送信する

**状態遷移を正しく構造化すれば両問題とも構造的に解決する**(取得と送信が分離され、IDLEでは
どちらも起きない)。

### ユーザーの確定した設計判断

- **IDLE中**: センサーデータ取得も送信もしない。ただし「**IDLE状態であることを示す軽量コマンド**」
  (新規 `FRAME_CMD_IDLE_BEACON`)を低頻度(1Hz)で送る → app.pyは「生きているがIDLE」と分かる。
- **照度と音圧は例外**: IDLE中もこの2つだけは取得してよい。これにより `Trigger_Poll()` の
  照度/音圧トリガー(=ファームがフラグを立てて状態遷移する経路、memo.md:51-53)がIDLE中も
  生き続ける。**取得はするが送信はしない**(トリガー判定専用)。
- **センサー周期指定**: **センサー種別ごとに個別指定**(env/light/tof/motion)。
- **全センサーの取得周期は最低10Hz**(下記§3参照)。
- **優先度**: 状態遷移再構築(Step 1-4)が最優先。残タスク(§7)はその後。

### 設計判断: 共有データ構造の「クラス化」

要求「センサーデータの保存は構造体を用いてクラス化し、プロジェクト全体で共有する」について、
**`FullStatus_t`(165B、`comm_dto.h`)は165Bレイアウト凍結のため構造体自体は変更できない**
(ガードレール)。代わりに **`sensor_store.h/.c` を新設**し、`FullStatus_t` の**単一インスタンスを
このモジュールが所有**する。`app_state.c` は `ctx->st` を直接触らず、このAPI経由でのみ
アクセスする(取得=上書き、送信=読み出し)。これが要求の「クラス化して共有」の実体。

## 3. センサー10Hz化: ハード制約との突き合わせ(**必読**)

要求「全てのセンサー取得周期の最低値を10Hz」を**実機のハード制約と照合した結果**:

| センサー | 現在の取得周期 | **新: 取得周期** | ハード上限 | 判定 |
|---|---|---|---|---|
| **温度・湿度** (HTS221) | 100ms (10Hz) | **100ms (10Hz)** | **ODR 12.5Hz が最速**(選択肢は 1/7/12.5Hz のみ、[hts221_reg.h:375-378](../Drivers/BSP/Components/hts221/hts221_reg.h#L375)) | ✅ 10Hz可(ODR 12.5Hz > 10Hz なので毎回新しい値が読める) |
| **気圧** (LPS22HH) | 100ms (10Hz) | **100ms (10Hz)** | ODR 75Hz 設定済み | ✅ 余裕 |
| **照度** (VEML3235) | 200ms (5Hz) | 取得呼び出しは100ms周期(**実測は約5Hzのまま**) | 積分時間 **IT50(50ms) が最速**、現状はドライバ既定。[veml3235_reg.h:48-52](../Drivers/BSP/Components/veml3235/veml3235_reg.h#L48) に IT50/100/200/400/800 | ⚠️ **IT100設定は反映確認済みだが実測5Hz止まり**(下記) |
| **ToF距離** (VL53L5CX) | 500ms (2Hz) | **100ms (10Hz)** | 4x4 なら最大60Hz。現在 profile が `Frequency=5Hz`/`TimingBudget=30ms` に絞っている | ⚠️ **要 profile変更**(Step 4) |
| **加速度・ジャイロ** (ISM330DHCX) | 毎回 | **毎回(=送信レート)** | ODR 208Hz | ✅ 既に10Hz超 |
| **地磁気** (IIS2MDC) | 毎回 | **毎回(=送信レート)** | ODR 100Hz | ✅ 既に10Hz超 |

### 10Hz化に必要な追加変更(Step 3/4に織り込み済み)

1. **照度**: 取得周期を200ms→100msにするだけでは不十分。**積分時間(IT)を100ms以下に設定**する
   必要がある(IT200のままだと100ms周期で読んでも中身が200msごとにしか更新されない)。
   ただし `VEML3235_Init()` は内部で `VEML3235_Pwr_On()`(SHUTDOWNビットクリア)を呼び
   既にキャプチャ中の状態で返るため、`SetExposureTime()` をInit直後に呼んでも反映されない
   (実機で確認済み)。正しい順序は `Init()` → `Stop()` → `SetExposureTime(0, 0U)`
   (`VEML3235_CONF_IT100` = レジスタ生値 `0`、ミリ秒値ではない) → `Start()`
   ([b_u585i_iot02a_light_sensor.h:185](../Drivers/BSP/B-U585I-IOT02A/b_u585i_iot02a_light_sensor.h#L185))。
   `NonSecure/Core/Src/sensors.c` の `Sensors_Init()` で実装・実機のレジスタ読み戻しで
   IT100反映を確認済み。**それでも実測の値更新周期は約200ms(5Hz)止まりで、100ms(10Hz)
   までは短縮できなかった**(VEML3235内部の測定サイクルに起因すると推測、データシート未精査)。
   ユーザー確認済み: 「5Hzを実測上限として受け入れ、Step 3を完了とする」。
   IT を短くすると暗所での感度が落ちるトレードオフもある(要実機確認、深追いはしない)。
2. **ToF**: 取得周期を500ms→100msにするなら profile の `Frequency` も 5→10Hz以上に上げる
   (Step 4)。**`TimingBudget=30ms` は `Frequency=10Hz`(=100ms周期)なら収まる**が、
   I2C読み出しに約35msかかるため、10Hzで読むと**ループの約35%をToFのI2Cが占める**。
   `[PROF]` の loops/s と 50Hz テレメトリが崩れないか**必ず実測**すること。崩れるなら
   ToFだけ200ms(5Hz)に戻す判断を許容する(**要求より実機の安定性を優先**)。
3. **温湿度**: ODR 12.5Hz が物理上限なので、**取得周期100ms(10Hz)が要求を満たす最善**。
   ユーザー確認済み: 「12.5Hzのまま読み出しは10Hzで行う」。

### 下限クランプ値(Step 3で実装)

コマンドで周期を指定できるようにするが、**ハード制約を割る値はクランプ**する
(割るとI2Cがループを圧迫し、既に解消済みの停止クラスの問題が再発する):

| sensor_id | 名前 | 既定 | **下限クランプ** | 根拠 |
|---|---|---|---|---|
| 0 | env | 100ms | **80ms** | HTS221 ODR 12.5Hz = 80ms |
| 1 | light | 100ms | **50ms** | VEML3235 IT50 = 50ms |
| 2 | tof | 100ms | **50ms** | I2C 約35ms/read |
| 3 | motion | 0(毎回) | **0** | 0=毎回。ODR 208Hz なので実質5ms |

上限は一律 **60000ms**。クランプしたら `printf("[SENS] period clamped ...")` で残す。

### Step 1: `sensor_store` を新設し、取得と送信の境界を作る(挙動不変)

- **目的**: `FullStatus_t` の単一所有者を作り、以降のStepで「取得」と「送信」を分離できる土台にする。
  このStepでは**挙動を変えない**(リファクタのみ)。

- **API骨格**(`FullStatus_t` のレイアウトは触らない。所有権だけを移す):
```c
/* センサーデータの単一保管庫。プロジェクト全体でこのインスタンスのみを共有する。
 * 取得(AcquireXxx)で上書きし、送信側は GetForSend() で読むだけ。 */
void                SensorStore_Init(void);
/* データ取得状態: 全センサーを読んで保管庫を上書きする(env/motion/tof/light/audio/MCU)。 */
void                SensorStore_AcquireAll(void);
/* IDLE用の例外取得: トリガー判定に要る照度と音圧だけを更新する。 */

/* データ送信状態: 保管庫の現在値を読む(取得はしない)。 */
const FullStatus_t *SensorStore_GetForSend(void);
/* Trigger_Poll() に渡す用(読み取り専用の同一インスタンス)。 */
const FullStatus_t *SensorStore_Peek(void);
```
- **変更**: `NonSecure/Core/Src/app_state.c` の `build_status()` を `sensor_store.c` へ移し

### Step 2: IDLEでは取得も送信もしない + IDLE_BEACONを送る

- **目的**: 要求の中核。**問題1を根治**する。
- **新規コマンド**: `FRAME_CMD_IDLE_BEACON = 0x14`。
  - `Secure/Core/Inc/frame_codec.h` と `pc_side/status_monitor/protocol.py` に
    **同一値・同一コミット**で追加(不一致は無言の通信断)。
  - payload: `[uptime_ms u32 LE][device_state u8]`(5B)。センサー値は載せない。
- **変更**: `NonSecure/Core/Src/app_state.c` のIDLEブロック(現156-168行)を書き換える:
```c
if (ctx->state == STATE_IDLE)
{
  /* 要求: IDLEでは「uartのdma/フラグ/BLE・WiFiコマンドを待機」する以外の動作をしない。
   * 例外として照度・音圧だけは取得する - Trigger_Poll() の TRIG_LIGHT/TRIG_AUDIO
   * (=ファームウェア自身がフラグを立てて状態遷移する経路)がIDLE中も生きるように。
   * 取得はするが送信はしない(トリガー判定専用)。 */
  SensorStore_AcquireTriggerInputs();

  /* データではなく「IDLEで生存中」だけを低頻度で知らせる。 */
  if ((int32_t)(now_ms - ctx->nextBeaconMs) >= 0)
  {
    ctx->nextBeaconMs = now_ms + CFG_IDLE_BEACON_MS;
    Comm_SendIdleBeacon((uint32_t)ctx->state);
  }
  ctx->haveAcquired = 0U;
  return;
}
```
- **新規NSCゲートウェイ** `void Comm_SendIdleBeacon(uint32_t state)`(既存7つは不変、追加は可):
  4ファイル対で追加 — `NonSecure/Core/Inc/comm_api.h` / `Secure/Core/Src/secure_nsc.c`
  (`CMSE_NS_ENTRY`、スカラー引数のみなので `cmse_check_address_range` は不要) /
  `Secure/Core/Inc/comm_backend.h` / `Secure/Core/Src/comm_service.cpp`
  (`CommBridge_SendIdleBeacon` 実体。既存 `CommBridge_TakeExplicitWake` と同じ書式)。
  実体は `Frame_Encode(FRAME_CMD_IDLE_BEACON, ...)` して `comm_uart::SendAsync` +
  `comm_wifi::SendRaw`(既存 `sendUart`/`sendTcp` と同じ経路)。
- **設定追加**: `NonSecure/Core/Inc/app_config.h` に `CFG_IDLE_BEACON_MS = 1000U`(1Hz)。
  `CFG_IDLE_TELEMETRY_MS` は**用済みなので削除**(コメントも要求に合わせて書き換える)。
  `AppStateCtx_t` に `uint32_t nextBeaconMs;` を追加、`nextTelemetryMs` は削除。
- **app.py**: `_poll_queue` の `decode_status` 呼び出し**より前**に `CMD_IDLE_BEACON` 分岐を
  追加(既存 `CMD_LOG_RESP`/`CMD_ACK` 分岐と同じ位置・書式)。受信したら状態ラベルを
  "IDLE(待機中)" に更新し `_log` に出す。**センサー値は更新しない**(IDLE中は値が古いままで
  あることがUI上も分かるように)。
- **ビルド**: Secure + NonSecure。`NS_APP_VERSION` を **31** に。
- **検証(PASS)**:
  1. app.pyでUART接続 → ACTIVE時 約50fps。

### Step 3: センサー周期をコマンドで指定 + 既定を全て10Hzに

- **目的**: 要求「センサー周期はコマンド上で指定できる機構を追加」+「全センサー最低10Hz」。
  **問題2への主対応**。
- **新規コマンド**: `FRAME_CMD_SET_SENSOR_RATE = 0x15`、payload `[sensor_id u8][period_ms u16 LE]`。
  `frame_codec.h` と `protocol.py` に同一追加。`sensor_id`: `0=env, 1=light, 2=tof, 3=motion`。
- **既定周期を10Hzに変更**(`NonSecure/Core/Src/sensors.c`):
  - `SENSORS_ENV_PERIOD_MS` 100 → **100**(据え置き。HTS221 ODR 12.5Hz が上限のため10Hzが最善)
  - `SENSORS_LIGHT_PERIOD_MS` 200 → **100** (10Hz)
  - `SENSORS_TOF_PERIOD_MS` 500 → **100** (10Hz)
  - motion: 周期なし(毎回) → `s_motionPeriodMs = 0`(0=毎回、現状維持)
- **照度の積分時間を短縮**(10Hz化に必須): `Sensors_Init()` に
  `(void)BSP_LIGHT_SENSOR_SetExposureTime(0, 100);` を追加(IT200→IT100)。
  **IT を短くすると暗所の感度が落ちる**ので、実機で照度値が妥当か確認する。
- **`sensors.h` に追加**: `void Sensors_SetPeriod(uint8_t sensor_id, uint16_t period_ms);`
  `sensors.c` の `SENSORS_*_PERIOD_MS` の `#define` を **static変数化**
  (`s_envPeriodMs=100, s_lightPeriodMs=100, s_tofPeriodMs=100, s_motionPeriodMs=0`)し、
  motionブロックにも周期判定を入れる(0なら毎回)。
- **⚠️ 下限クランプ(必須)**: §3の表の通り。`Sensors_SetPeriod` 内でクランプし、
  クランプしたら `printf("[SENS] period clamped ...")`。上限は一律60000ms。
- **Secure→NonSecure 伝達**: 新規NSCゲートウェイ
  `uint32_t Comm_TakeSensorRateCmd(uint8_t *sensorId, uint16_t *periodMs);`
  (戻り値: 1=取得した/0=なし。**既存 `Comm_TakeExplicitWake` と同じ「一回消費」パターン**)。
  4ファイル対で追加。Secure側は `handleFrame` の `FRAME_CMD_SET_SENSOR_RATE` case で
  `pendingSensorRate{id, period, valid}` に積み(既存 `explicitWakeRequested` と同じ
  file-scope volatile パターン)、ACKを返す(既存 `FRAME_CMD_ENTER_COMM` case が実例)。
  **ポインタ引数があるので `secure_nsc.c` 側で
  `cmse_check_address_range(..., CMSE_NONSECURE|CMSE_MPU_READWRITE)` 検証 + Secureローカル
  コピーが必須**(既存 `Comm_GetMcuInfo` が実例)。
- **NonSecure側で消費**: `AppState_Tick` の冒頭(Trigger_Poll の前)で
  `uint8_t id; uint16_t p; if (Comm_TakeSensorRateCmd(&id, &p)) Sensors_SetPeriod(id, p);`
- **app.py**: センサー周期設定UI(4センサー分のスピンボックス+適用ボタン)。送信は既存
  `_sync_time`/`_send_standby` と同じ `self.transport.write(protocol.build_frame(...))` パターン。
- **ビルド**: Secure + NonSecure。`NS_APP_VERSION` を **32** に。
- **検証(PASS)**:
  1. **10Hz化の確認**: 全データタブで 照度・ToF・温湿度の値が**10Hz相当で更新**されること
     (値の変化頻度で判断)。特にToFが 2Hz→10Hz、照度が 5Hz→10Hz。
  2. **50fpsのUARTテレメトリが乱れないこと**、`overrun=0`、`[PROF]` の loops/s が極端に
     落ちていないこと(**ToFのI2Cがループを食う懸念。崩れたらToFだけ200msに戻す**)。
  3. app.pyから `tof=200ms` を送る → ACK受信、ToF更新が5Hzに落ちる。
  4. **下限クランプ確認**: `tof=10ms` を送る → `[SENS] period clamped` が出て 50ms に留まり、
     50fpsのテレメトリが乱れないこと。
  5. `ENTER_COMM` でのIDLE復帰が引き続き5回連続成功。
- **コミット**: `feat(sensors): 10 Hz default acquisition, per-sensor period settable by command`

### Step 4: ToF profile を10Hzに合わせる

- **目的**: Step 3で `tof` 周期を100msにしても、**センサー側の profile が
  `Frequency=5Hz`/`TimingBudget=30ms` なので実効レートが5Hz止まり**。ここを合わせる。
- **対象**: `NonSecure/Core/Src/sensors.c` の `tofInitAndStart()`(現38-43行):
  `profile.RangingProfile = RS_PROFILE_4x4_CONTINUOUS; profile.TimingBudget = 30; profile.Frequency = 5;`
- **変更**: `profile.Frequency = 5` → **10**(4x4なら最大60Hzまで可)。`TimingBudget=30` は
  100ms周期に収まるので**据え置きでよい**が、実測で精度が落ちるようなら調整。
- **⚠️ 注意**: ToFのI2C読み出しは約35ms/read。10Hzで読むと**ループの約35%をToFが占める**。
  `[PROF]` の loops/s と 50Hz テレメトリが崩れないか**必ず実測**。崩れるなら
  **要求より実機の安定性を優先**し、ToFだけ200ms(5Hz)に戻す(`s_tofPeriodMs=200`、
  `Frequency=5`)判断を許容する。その場合は計画に実測値とともに理由を追記すること。
- **検証(PASS)**: ToF更新が実測で**10Hz**、かつ UART 50fps・`overrun=0` が維持されること。
- **コミット**: `perf(sensors): raise the ToF ranging profile to 10 Hz to match the poll period`
- **実機検証結果**: 15秒間でSTATUS 741フレーム(49.4fps)、CRCエラー0。ToF更新間隔
  実測avg 109ms(≒9.2Hz、目標10Hzにほぼ到達)。50Hzテレメトリの崩れなし。**PASS、採用**。

### 7-1. NVMログのリセット跨ぎ永続化バグ(**解決済み・2026-07-17実機検証**)

- **症状**: 特定の操作の後に `LOG_REQ` でログ件数が大きく減る(実際には「電源投入直後からの
  新規カウントに戻る」)。
- **実機で切り分けた原因**: `TAMP->BKP1R`(ヘッドポインタの旧保持先)は**SWD経由の
  ハードリセット/ソフトリセットでは正しく保持される**が、**USBケーブル抜き差し(VBAT
  ドメインへの供給電源自体が落ちる完全電源断)では消える**。本ボードはコイン電池等の
  VBATバックアップを実装していないため、USB給電が切れるとTAMP/RTCドメインも道連れで
  初期化される。ハードウェア制約であり、`TAMP->BKP1R` の使い方自体に誤りは無かった。
- **修正**: ヘッドポインタをTAMPレジスタに頼らず、**NOR自体から復元できる方式**に変更した
  (`Secure/Core/Src/nvm_log.cpp`)。各4KBサブセクタの先頭8Bを
  `SubsectorHeader{magic, seq}` として予約し、`seq`にそのサブセクタが始まる絶対レコード
  番号を記録する。起動後最初のアクセス時に `scanHeadIndexFromNor()` が全16サブセクタの
  ヘッダを読み、最大`seq`のサブセクタ内を先頭から走査して書き込み済み件数を数え、
  `headIndex` をSRAMにキャッシュする(以後は電源が入っている間だけの通常変数)。
  1レコード13B・ヘッダ8Bで `kRecordsPerSubsector` は315→314に微減(容量5040→5024)。
- **既に修正済みの別バグ**(参考): 消去完了直後に同一`Poll()`フロー内で
  `offsetInSubsector(absIndex)==0` に再度合致し、書き込み前に無限に同じサブセクタを
  消去し続けていた(`lastErasedSubsectorPlus1_` で解決済み、今回のヘッダ書き込みも
  同じ`atSubsectorStart`判定に相乗り)。
- **実機検証結果**(2026-07-17): USB完全電源断を跨いでログが継続することを確認
  (電源断前31件 → 電源断直後の新規ログはtick_ms=14039からだが絶対インデックスは16から
  連番で継続、断後の総数36件)。SWDハードリセット(12→20件)、書込+ソフトリセットでも
  継続を再確認。IDLE→ENTER_COMM復帰5/5、50Hzテレメトリ51.9fps・CRC0で回帰なし。
- **コミット**: `fix(log): recover the nvm_log head from NOR subsector headers instead of TAMP->BKP1R`
- **関連ファイル**: `Secure/Core/Src/nvm_log.cpp`、`Secure/Core/Inc/nvm_log.hpp`。

### 7-2. LOG_RESETボタンの実機確認(**完了・2026-07-17実機検証**)

### 7-3. BLEで全センサーデータを送る(**完了・2026-07-17実機検証**)

- **設計**: 既存 `MiniStatus`(39B、`FRAME_CMD_STATUS_MINI`)は**一切変更していない**。別経路として
  `PumpRecTx()` と同じ**生TLV方式**(`Frame_Encode` を使わない)で
  `FRAME_CMD_STATUS_FRAG`(0x16)を新設。ヘッダは
  `[cmd u8][seq u16 LE][frag_idx u8][55Bスライス]`(4+55=59B、AT特性長64B以内)。
  `FullStatus`(165B = 55×3)をちょうど3等分のフラグメントに分割し、`comm_ble::SendStatusFrag()`
  が呼ばれるたびに1フラグメントだけ送る。呼び出し元(`Service::poll()`)は
  `CFG_TLM_BLE_FRAG_PERIOD_MS`(1000ms)ごとに1回呼ぶので、約3秒で1周(≒0.33Hzの
  フルスナップショット)。`IsRecTxActive()` で音声送信中は停止(`SendStatus`と同じゲート)。
  **WB5MMGの再フラッシュは不要**(BLEは既に115200baud化・10Hz化済みで余裕がある)。
- **理由**: 真の制約はBLE GATT特性長(64B)ではなく**160BのATヘックス文字列バッファ**であり、
  過去に47Bペイロードで `str_received` オーバーフローを踏んでいる。
- **PC側**: `protocol.py` に `CMD_STATUS_FRAG`/`decode_status_frag_header`/`FRAG_COUNT`/
  `FRAG_PAYLOAD` を追加。`app.py` に新規タブ「BLE全データ」(`_build_ble_alldata_tab`)と
  再構成ロジック(`_handle_ble_status_frag`)を追加。既存の「全データ」タブ
  (UART/TCP/BLE共通、MiniStatus由来)とは別ツリーで、BLEで受信した完全な
  `FullStatus` だけを表示する。
- **実機検証**(2026-07-17、bleak直結スクリプト): P2PSRV1へ接続し15秒間観測。
  MiniStatus notify 153件(≒10Hz)と並行してSTATUS_FRAGが3個ずつ届き、4回分の
  FullStatus再構成に成功(`uptime_ms` が889671→892671→895671→898671と3秒刻みで
  正確に増加、フラグメント順序の乱れなし)。同時刻のUARTスナップショットと
  temp/hum/press/tofの値が近似一致(センサーは連続変動するため厳密一致ではないが
  同じセンサーを見ている値として妥当)。UART側の回帰確認(50Hzテレメトリ51.7fps・
  CRC0、IDLE→ENTER_COMM復帰5/5)も合わせて実施し、既存経路への影響なしを確認。
- **コミット**: `feat(ble): fragment the full sensor set across notifies with PC-side reassembly`
