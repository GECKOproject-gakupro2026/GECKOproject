# B-U585I-IOT02A 人声・非人声分類 段階実装計画

- 対象: B-U585I-IOT02A / STM32U585
- 目標: マイク入力を「人間の声」「非人声」の2クラスに準リアルタイム分類する
- 基準リポジトリ: [Fly0KUBOKI/B-U585I-IOT02A](https://github.com/Fly0KUBOKI/B-U585I-IOT02A)
- 基準commit: `b81448c1c2668184febd11551f65748acde0495d`
- 作成日: 2026-08-22

## 1. 実装方針

初回成功を優先し、次の順序で進める。

1. 既存の音声取得・ストリーミングが再現できることを確認する。
2. PC上で人声／非人声の分類を成立させる。
3. 既存のSecure側AI実行経路へモデルを組み込み、ST-LINKで書き込む。
4. 保存済み音声窓を使った単発推論を成功させる。
5. リングバッファと平滑化を追加し、連続判定する。
6. 実機回帰試験後、必要に応じてNonSecure移設とOTAを行う。

初期段階では、OTA、AIのNonSecure移設、モデル単体更新を必須条件にしない。これらを同時に変更すると、音声取得、モデル、生成コード、TrustZone、OTAのどこが原因か分離できなくなるためである。

## 2. 最初の完成状態

STM32が16 kHzモノラル音声を継続取得し、直近約1秒の音声について250 msごとに次を出力する。

```text
[VOICE] class=speech p=0.91 rms=842 inference_ms=72
[VOICE] class=non_speech p=0.08 rms=215 inference_ms=71
```

初期合格条件:

| 指標 | 合格基準 |
|---|---:|
| PC独立test balanced accuracy | 90%以上 |
| speech recall | 85%以上 |
| non-speech recall | 85%以上 |
| int8化によるaccuracy低下 | 2ポイント以内 |
| 実機known-answerのクラス一致 | 全件一致 |
| 実機推論時間 | 250 ms未満 |
| 連続動作 | 1時間、停止・HardFaultなし |

これはPoC用の暫定値である。データ数が少ない間は性能保証値として扱わず、データセット版と一緒に記録する。

## 3. モデル選定

### 3.1 2段階で選定する

| 段階 | モデル | 目的 |
|---|---|---|
| A: 統合確認 | 現行raw PCM 1D-CNN | 既存`train.py`、`stedgeai`、`ai_app.cpp`を最小変更で通す |
| B: 本分類器 | log-mel + MiniResNetV2 1-stack相当のsmall CNN、full-int8 | 人声／環境音の頑健な分類 |

段階Aの精度は最終評価に使わない。STM32向け生成・リンク・呼出し・出力確認のためのスモークテストとする。

### 3.2 本分類器をlog-mel方式にする根拠

- 人声の判別には、時間波形そのものより時間周波数構造を使う方が、位相や振幅変化に対して扱いやすい。
- ST公式のAudio Event Detection例は、B-U585I-IOT02Aを対象とし、log-mel特徴とint8モデルを扱っている。
- 公式MiniResNetV2 1-stackの公開値は、B-U585I-IOT02Aで実行可能なFlash/RAM範囲に収まるため、初期候補として妥当である。

ただし、公式モデルのクラスをそのまま使うのではなく、人声／非人声データで再学習または転移学習し、2出力にする。

### 3.3 初期前処理

ST公式AED例との整合を優先し、以下から開始する。

| 項目 | 初期値 |
|---|---:|
| sample rate | 16,000 Hz |
| channel | mono |
| PCM | signed 16-bit |
| analysis window | 400 samples = 25 ms |
| hop | 160 samples = 10 ms |
| FFT | 512 points |
| mel bands | 64 |
| patch | 96 frames |
| 1入力の実時間長 | $(96-1)\times160+400=15,600$ samples = 0.975 s |
| 推論更新周期 | 250 msから開始 |

PCとSTM32で同一パラメータを使用し、特徴量のknown-answer testを作る。パラメータをCコードとPythonへ二重記述せず、`preprocessing.yaml`から生成する。

## 5. Step-by-step実装

### Step 0: 基準状態を固定する

### 作業

1. `feature/ml-voice-classification-test`を`master`の`b81448c1`から作成する。
2. STM32CubeIDE、STM32CubeProgrammer、ST Edge AI Core、Python、TensorFlowの版を記録する。
3. 現行Secure/NonSecureプロジェクトを変更せずビルドする。
4. ST-LINKで書き込み、起動ログ、センサーテレメトリ、音声ストリーミングを確認する。
5. ELF、bin、map、ビルドログを基準成果物として保存する。

### 確認コマンド例

```powershell
python pc_side/status_monitor/app.py
python pc_side/ml_pipeline/pipeline.py --help
```

### 完了条件

- 現行commitをクリーンビルドできる。
- PCツールから`a`で音声ストリーム開始、`s`で停止できる。
- 無音と発声でRMS/peakが明確に変化する。
- 使用ツール版とmapファイルを記録できる。

### 問題時

この段階で失敗した場合はAI実装へ進まず、クロック、MDF1、GPDMA、Secure Gateway、UART/TCPのどこで音声が止まるかを切り分ける。

### Step 1: 実機音声を収録する

### 作業

1. 既存の音声ストリーム／録音機能で16 kHz mono WAVを保存する。
2. 1ファイルを1収録セッションとし、途中で細切れにしない。
3. speechとnon_speechを異なる日、距離、方向、部屋で収録する。
4. 各ファイルに`session_id`、距離、環境、ラベル、SHA-256を記録する。
5. train/validation/testを**収録ファイル単位**で分ける。

### 最小データ収録案

| クラス | 内容 | 最小収録量 |
|---|---|---:|
| speech | 男女、通常会話、短い発声、遠近、正面／側面 | 合計30分以上 |
| non_speech | 無音、空調、机上振動、足音、ドア、音楽、機械音、屋外音 | 合計30分以上 |

同じ話者だけでPoCを始めてもよいが、testには学習に含まれない話者を最低1名含める。音楽内の歌声は初期仕様では`speech`とするか`non_speech`とするか曖昧なため、収録前に定義する。初期推奨は「発声器官由来の声をspeech」とし、歌声もspeechに含める。

### manifest例

```csv
clip_id,path,label,split,session_id,speaker_id,environment,distance_cm,sample_rate,sha256
spk01_room1_001,dataset/raw/speech/spk01_room1.wav,speech,train,s01,p01,quiet_room,50,16000,...
noise_room2_001,dataset/raw/non_speech/fan_room2.wav,non_speech,test,s12,,fan,100,16000,...
```

### 完了条件

- 両クラス30分以上ある。
- testが独立話者・独立sessionを含む。
- 16 kHz、mono、16-bit以外を検出できる。
- 同一`session_id`が複数splitに存在しない。

### Step 2: PC側のデータ処理を実装する

### 作業

1. `prepare_dataset.py`でWAV検査、DC除去、必要時のみレベル正規化を行う。
2. 0.975秒の入力patchを作る。
3. speech区間に無音が多すぎるファイルを除外する。
4. non_speechへ、人声が混入していないか試聴・確認する。
5. `features.py`でlog-melを生成する。
6. raw PCMとlog-melの両方でknown-answerデータを保存する。

### データ拡張

- 音量変化
- 時間方向の微小シフト
- speechと背景雑音の混合
- 実機で観測した雑音の追加

pitchを大きく変える、過度なtime stretchを行うなど、実環境から外れる拡張は初期段階では避ける。

### テスト

```powershell
python -m pytest pc_side/ml_pipeline/tests/test_dataset_split.py
python -m pytest pc_side/ml_pipeline/tests/test_features.py
```

### 完了条件

- splitリークが0件である。
- 同じWAVから同じ特徴量が再生成される。
- 既知WAVの特徴量shape、範囲、hashが固定される。

### Step 3: PC上でベースラインを学習する

### 作業

1. 現行raw PCM 1D-CNNを2クラス用に変更し、統合確認モデルを作る。
2. log-mel + small CNNを学習する。
3. validationで閾値を選び、testは最後に1回評価する。
4. accuracyだけでなく混同行列、balanced accuracy、各クラスrecall、誤検出例を保存する。
5. 誤分類音声を再生し、ラベル誤り、混合音、低SNRを分類する。

### Step 5: STM32へ組み込み、ST-LINKで実行する

### 作業

1. 段階Aの小型raw PCMモデルを既存`Secure/Core/AI`へ統合する。
2. `ai_app.cpp`の入力shape、dtype、scale、zero-pointを生成モデルに合わせる。
3. 固定のknown-answer inputをFlashから推論し、PC結果と比較する。
4. 次に実マイクバッファから1回だけ推論する。
5. `i`コマンドで単発推論、`I`コマンドで連続推論を開始／停止できるよう整理する。
6. ST-LINKでSecureとNonSecureを通常手順どおり書き込む。

### 実行順序

```text
固定入力KAT
  -> 保存済みマイク窓
  -> 最新マイク窓
  -> 連続推論
```

### ログへ出す値

- model ID/version
- input dtype/shape/scale/zero-point
- speech/non_speech score
- raw判定
- 推論時間
- AI runtime error

### 完了条件

- known-answer全件でPCと実機のクラスが一致する。
- 実マイクに対して発声時と非発声時でscoreが変化する。
- 1,000回連続推論でruntime error、HardFault、メモリ破壊がない。

ここまで成功するまではOTAへ進まない。

### Step 6: 本モデルとSTM32前処理を統合する

### 作業

1. Secure側に16,000 samples以上の音声リングバッファを確保する。
2. 既存Gatewayを用いて最新0.975秒窓を取得する。
3. STM32上でlog-mel特徴を計算する。
4. PCで作った特徴量known-answerと要素ごとに比較する。
5. log-mel int8モデルを統合する。
6. 前処理時間と推論時間を個別計測する。

### 重要な切り分け

PCと実機で判定が異なる場合、次の順に確認する。

1. PCM窓の開始位置、長さ、符号、エンディアン
2. DC offsetとscale
3. window関数
4. FFT値
5. mel filter bank
6. log変換とclamp
7. int8量子化scale/zero-point
8. モデル出力のdequantize

### 完了条件

- PC/STM32のlog-mel特徴量誤差が規定値内。
- 本モデルのknown-answer全件一致。
- 前処理＋推論が250 ms以内。
- Flash/RAM予算内。

### Step 7: リアルタイム判定を実装する

### 状態処理

モデルの1回の出力をそのまま状態にしない。開始時は次から実装する。

```text
推論窓: 0.975秒
更新周期: 250 ms
speech開始: p(speech) >= 0.70 が3回連続
speech終了: p(speech) <= 0.40 が3回連続
0.40 < p < 0.70: 現在状態を維持
```

閾値と連続回数はvalidationデータと実機ログから調整する。これはチャタリングを抑制し、瞬間的な衝撃音を人声と誤判定しにくくするためである。

### スケジューリング

1. 音声DMAは停止しない。
2. 250 msごとに最新窓のsnapshotを作る。
3. 前処理・推論中もDMA書込み領域との競合を避ける。
4. 推論が周期を超えた場合、キューを蓄積せず古い窓を破棄する。
5. `inference_ms`、deadline miss、ring overflowを計測する。

### 完了条件

- 近距離／遠距離の発声に反応する。
- 無音、拍手、机を叩く音、空調、音楽を評価できる。
- 1時間動作でdeadline miss率1%未満。
- 状態変化とscoreをPCへ継続送信できる。

### Step 8: 実機評価と再学習ループを作る

### 試験セット

| 条件 | 例 |
|---|---|
| 話者 | 学習済み話者、未知話者、男女 |
| 距離 | 0.3 m、1 m、3 m |
| SNR | 静かな室内、空調、音楽併存 |
| 非人声 | 無音、拍手、物音、足音、ドア、機械音 |
| 混合 | speech + fan、speech + music |

### 失敗例の扱い

1. 音声とscoreを時刻同期して保存する。
2. 誤検出を`false_positive`、見逃しを`false_negative`へ分類する。
3. 人がラベルを確認する。
4. 元testデータは変更せず、新しいデータセット版を作る。
5. 再学習後、過去のtestセットすべてで回帰評価する。

### 完了条件

- テスト条件ごとの混同行列が得られる。
- 誤分類音源を追跡できる。
- 新モデルが過去モデルより悪化していないことを確認できる。

### Step 9: AIをNonSecureへ移す

初回分類成功後に実施する。

### 作業

1. `NetworkRuntime...CM33_GCC.a`と生成コードをNonSecureへリンクする。
2. `ai_app.cpp`、前処理、状態判定を`NonSecure/Core/AI`へ移す。
3. 音声取得はSecureに残し、`Comm_GetAudioBuffer`を利用する。
4. Secure版とNonSecure版のknown-answer、実マイク出力、処理時間を比較する。
5. Secure側AIコードを削除する。

### 完了条件

- NonSecure側で同じモデル結果が得られる。
- 音声、通信、センサー、IDLE復帰に回帰がない。
- Secure側のFlash/RAM削減をmapで確認する。

### Step 10: OTAを追加する

分類がST-LINK書込みで安定してから実施する。

### 第1段階

AIモデル・生成コード・ランタイムを含むNonSecureファームウェア全体をOTAする。

### 作業

1. OTA対象binがSecure ELFではなくBank2向けNonSecure ELF由来であることを検査する。
2. vector table、load address、size、SHA-256を適用前に検査する。
3. 適用後の直接ジャンプを`NVIC_SystemReset()`へ置換する。
4. AI初期化とknown-answer成功後にboot confirmする。
5. 失敗時に旧イメージへrollbackする。
6. 正常、破損、電源断、連続10回OTAを試験する。

### 完了条件

- 10回連続で更新・再起動・自己試験が成功する。
- 転送中、消去中、書込み中、boot確定前の電源断から復旧する。
- AI自己試験失敗時に旧版へ戻る。

モデル単体OTAは、生成コードとruntime ABIを固定し、外部重みの安全なロードが確認できるまで実装しない。

## 8. 最初の作業単位
