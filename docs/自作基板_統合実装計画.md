# STM32U575 + ESP32-C3 自作基板 統合実装計画

> 状態: 自作基板フェーズの唯一の現行計画（Source of Truth）
> 作成: 2026-07-21
> 対象ブランチ: `plan/custom-board-u575-c3`
> 対象部品: `STM32U575QII6Q` / `ESP32-C3-WROOM-02-H4`

## 1. 目的と完成条件

評価ボードで成立したセンサー／音声取得、エッジAI推論、通信、ログ、OTAを、
自作の低消費電力モジュールへ移植する。

- STM32がセンサー／音声取得と推論を担当し、学習後はネットワークなしで判定を完了する。
- ESP32-C3がWi-Fi、BLE、配布ファームウェアの受信・検証・STM32への転送を担当する。
- 学習用モードでは音声を16 kHz・16 bit・mono以上で欠落なくWi-Fi送信する。
- 運用モードでは原則として判定結果だけをBLE送信し、Wi-Fiは停止する。
- 電源不足時にFlashを壊さず、安全に通信停止または更新中断できる。
- 電池／ソーラーの実測条件に基づくエネルギー収支が正である。

## 2. アーキテクチャ

### 2.1 責務

| 機能 | STM32U575 | ESP32-C3 |
|---|---|---|
| センサー、PDMマイク、前処理、AI推論 | 主担当 | 対象外 |
| Wi-Fi / BLE | データ生成 | 主担当 |
| 自身の安全な更新適用 | 主担当 | イメージ取得・配布管理 |
| 製品全体の版／manifest管理 | 状態報告 | 主担当 |
| 蓄電量監視、ESP電源ON/OFF | 主担当 | 自己保持要求のみ |

「ESPがファームウェアを管理する」は、ESPがSTM32のFlashを直接書く意味ではない。
ESPは署名付きbundleを取得・検証して分割転送し、STM32 Secure側がinactive bankへ書込み、
検証、切替、rollbackを行う。既存のTrustZoneとBootGuard境界は維持する。

### 2.2 動作モード

| モード | STM32 | ESP32-C3 | 無線 |
|---|---|---|---|
| `ENERGY_SAFE` | RTC/電源監視のみ | 電源断 | なし |
| `MONITOR` | センサー取得、推論、Stop 2活用 | 電源断 | なし |
| `BLE_RESULT` | 判定結果をqueueへ格納 | 送信時だけ起動 | BLEのみ |
| `LEARN_WIFI` | 生音声を連続供給 | PCへ転送 | Wi-Fiのみ |
| `UPDATE` | inactive bankへ書込み | bundle取得・転送 | 原則Wi-Fi |
| `SERVICE` | 診断、ログ | USB/UART診断 | 開発時のみ |

BLE常時接続が必要ならESPの電源断は使えない。接続間隔とLight-sleepを含む電力予算を
別途実測し、`BLE_RESULT`の成立条件を更新する。

## 3. コア仕様と制限

### 3.1 STM32U575QII6Q

| 項目 | 仕様／影響 |
|---|---|
| CPU | Arm Cortex-M33、TrustZone、DSP、単精度FPU、最大160 MHz |
| メモリ | Flash 2 MB（dual bank、read-while-write、ECC）、SRAM 786 KB（ECC使用時は減少） |
| パッケージ | UFBGA132、7 x 7 mm、0.5 mm pitch。実装、X線、via設計を製造業者と確認 |
| 温度 | suffix `6`: 周囲 -40～85 ℃、junction上限105 ℃ |
| `Q` suffix | 内蔵SMPS専用pinout。非Q品の回路／symbolは流用しない |
| 音声 | MDF（6 filter）とADF（sound activity detection）を使用可能 |
| 通信 | USB FS、USART/UART、SPI、I2C、SAI、OCTOSPI、FDCAN等。pin mux確認必須 |
| セキュリティ | TrustZone、HASH、TRNG等。U585固有のAES/PKA/OTFDECを前提にしない |
| 低電力 | LPBAM、Stop 2/3、Standby、Shutdown。保持SRAM増加は電流増加を伴う |

代表値は、SMPS・Flash実行・周辺clock停止・全SRAM有効、25 ℃、VDD=1.8 Vで
160 MHz時約10.5 mA。製品ページ上の代表的な低電力値はShutdown 160 nA、Standby
210 nA（RTCあり530 nA）、Stop 3は16 KB SRAM保持1.9 µA／全SRAM保持4.3 µA、
Stop 2は同4.0 µA／8.95 µA。条件と温度で大きく変わるため、製品判断にはtyp値だけでなく
対象温度のmax値と基板実測を使う。

### 3.2 ESP32-C3-WROOM-02-H4

| 項目 | 仕様／影響 |
|---|---|
| CPU | 32-bit RISC-V single core、最大160 MHz |
| メモリ | ROM 384 KB、SRAM 400 KB（16 KB cache）、RTC SRAM 8 KB |
| Flash | `H4`は4 MB Quad SPI。OTA、STM bundle、証明書、logの容量を先に配分 |
| 無線 | 2.4 GHz Wi-Fi 802.11b/g/n、Bluetooth 5 LE。Classic Bluetooth非対応 |
| BLE PHY | 125/500 kbps、1/2 Mbps。実効値はinterval、MTU、混信、再送で低下 |
| I/O | 最大15 GPIO、3 strapping GPIO。module内部Flash、boot等との競合確認必須 |
| antenna | PCB antenna。全層keep-outと筐体／電池からの離隔が必要 |
| 温度 | `H4`: 4 MB、周囲 -40～105 ℃、chip revision v0.4 |

module代表値はWi-Fi TX peak 280～345 mA、RX 82～84 mA、modem-sleep 13～28 mA、
Light-sleep 130 µA、Deep-sleep 5 µA、`CHIP_EN=Low` 1 µA。Wi-FiとBLEはradio/antennaを
共有するため、同時高負荷運用は避ける。

### 3.3 4 MB Flash制限

ESP-IDF bootloader、partition table、NVS、PHY、factory/recovery、`ota_0`、`ota_1`、
STM imageを無計画に同居させると4 MBを超える。実binaryを計測して以下から選ぶ。

1. ESP A/B OTAを維持し、STM imageは受信しながらstream転送する。
2. STM imageの一時保存が必要なら外部SPI NORを追加する。

単一ESP app partitionへの縮退は復旧性を失うため量産版では採用しない。

## 4. 電源要件と成立性

### 4.1 必須条件

#### STM32U575QII6Q

- `VDD`: 1.71～3.6 V。
- `VDDSMPS`: 1.71～3.6 V。SMPS使用時はVDDと同じ電源へ接続。
- `VLXSMPS`－`VDD11`: 2.2 µH ±20 %、Isat > 0.5 A、DCR < 200 mΩ。
- `VDD11`: 2 x 2.2 µF ±20 %、ESR < 20 mΩ @ 3 MHz、定格10 V以上。
- `VDDSMPS`: 10 µF ±20 %、ESR < 10 mΩ @ 3 MHz、定格10 V以上。
- 各VDD/VSS pairに100 nFを最短配置し、VDD系にbulk 10 µFを置く。
- `VDDA`: 使用機能により1.58～1.8 V以上、最大3.6 V。未使用でも浮かせない。
- `VDDUSB`: 3.0～3.6 V、`VDDIO2`: 1.08～3.6 V、`VBAT`: 1.65～3.6 V。
- 未使用の独立電源pinもdatasheet指定どおりVDDまたはVSSへ接続する。

値と結線はSTM datasheet Figure 25を回路図release時に一球ずつ照合する。

#### ESP32-C3-WROOM-02-H4

- `3V3`: 3.0～3.6 V、nominal 3.3 V。
- 外部電源能力: 0.5 A以上。設計値は過渡余裕を含め600 mA以上。
- module直近に10 µF + 0.1 µF、電源入口にも10 µF以上を置く。
- `EN`は浮かせず、rail安定後50 µs以上待ってHigh、reset時Lowを50 µs以上保持。
- ソーラー等の緩慢／不安定な電源ではRCだけに頼らず、約3.0 V thresholdのsupervisorを予約。
- ESP rail OFF時のphantom powerを防ぐため、接続pinをHi-Zにするかpower-off protectionを使う。

STM、ESP、sensorを共通3.3 V regulatorから供給する試作では、600 mAを全体定格と
読み替えず、ESPの600 mA設計値にSTM／sensor／損失の同時最大値を加えて選定する。

### 4.2 推奨構成

```text
solar ─ harvester/charger ─┐
                           ├─ storage ─ UVLO/protection ─┬─ always-on rail ─ STM32/sensors
primary coin cell ─────────┘                             └─ switched 3.3 V / >=600 mA ─ ESP32
                                                               ▲ load switch EN from STM32
```

solarと一次コイン電池は同一実装で充電しない。二SKUとして扱う。

- `BAT`: 非充電式コイン電池。充電経路なし。通常はWi-Fi禁止。
- `SOLAR`: solar + harvester + 充電可能storage。過充電／過放電／温度保護あり。

共通3.3 V railは試作しやすいがconverter静止電流が支配的になり得る。量産候補は
STM常時railとESP switched railを分離する。PMICは電池chemistry、最低入力、panelの
Voc/Vmp/Iscが決まるまで固定しない。

### 4.3 コイン電池とWi-Fi

一般的な小型一次コイン電池は345 mA peak / 500 mA供給要件を直接満たさない。
「コイン電池のみで任意時刻にWi-Fi送信」は禁止構成とし、以下から選ぶ。

- 学習時だけUSB／治具の外部電源でWi-Fiを許可する。
- 十分な蓄電capacitor/supercapacitorを充電し、energy閾値を超えた時だけWi-Fiを許可する。

bufferは概算 `C >= I * Δt / ΔV`、ESR降下は `ΔV = I * ESR` で別に評価する。
345 mAを0.5秒、0.3 V以内でbufferだけから支える理想値でも0.575 Fであり、実設計では
効率、DC bias、温度、劣化、marginを上乗せする。10 µFはenergy bufferにならない。

### 4.4 電力budget合格基準

| 入力 | 必要値 |
|---|---|
| 電源 | chemistry、容量、連続／pulse電流、内部抵抗、温度特性 |
| solar | 面積、Voc、Vmp、Isc、時間別照度、最悪無日照日数 |
| load | mode別平均／peak電流、時間、1日回数、converter効率 |
| loss | PMIC静止電流、switch漏れ、level shifter、sensor standby、自己放電 |

初期基準を `E_day_load <= 0.7 * E_day_harvest` とし、無日照期間をstorageだけで超えること。
一次電池はnominal容量でなく実pulse profileのusable容量から寿命を計算する。

## 5. ハードウェア計画

### H0: 要件凍結

- [ ] `BAT` / `SOLAR` / 外部電源併用を決定。
- [ ] Wi-Fi最長時間、頻度、距離と、BLE advertise/connection方式を決定。
- [ ] センサー、マイク、外部NORの型番と電圧／peak電流を確定。
- [ ] ESP 4 MBとSTM 2 MB dual-bankの実binary容量表を作成。
- [ ] 両部品の調達性、MOQ、PCN/lifecycleを確認。

Exit: mode別energy budgetと全rail連続／peak電流表が承認済み。

### H1: block、pin、interface

- [ ] 主data pathは`SPI + DATA_READY + WAKE/REQ`、保守経路はUARTとする。
- [ ] SPI master=ESP、STM=DMA slave。STMは`DATA_READY`で送信待ちを通知。
- [ ] UART、`ESP_PWR_EN/EN/BOOT`、`STM_NRST/BOOT0`をtest padへ出す。
- [ ] 電源断domain間の逆流を全signalで確認。
- [ ] PDM/MDF/ADF、I2C、OCTOSPI、SWDをCubeMXで割り当て、AF競合0件。
- [ ] 全strapping pinのreset時levelと外付けpullを表にする。

Exit: pin表、timing、電源sequence、recovery手順が確定。

### H2: 回路図

- [ ] STM Figure 25のSMPS、decoupling、BOR/PVD、clock、reset、SWDを実装。
- [ ] ESP reference schematicのEN、boot、decoupling、UARTを実装。
- [ ] ESP load switch、600 mA以上の3.3 V、supervisor、bulk実装余地を確保。
- [ ] STM、ESP、sensor rail別の電流測定jumper/shuntを設置。
- [ ] battery逆挿し、solar逆流、ESD、充放電、短絡保護を実装。
- [ ] Flash書込み中のUVLO thresholdとhold-upを計算。

Exit: ERC 0件、公式checklistに証跡あり。

### H3: PCB

- [ ] 原則4層（signal / solid GND / power / signal）。
- [ ] WROOM antennaをedgeに置き、antenna下／前方は全層keep-out。
- [ ] ESP電源loop、STM SMPS loop、PDM clockを小さくしRF/analogから分離。
- [ ] 0.5 mm BGA escape、via、mask、X-ray条件をDFM確認。
- [ ] crystal、SMPS、antennaから電池／筐体の磁性体を離す。
- [ ] 全rail、reset/boot、SWD、UART、SPI、wake/readyにtest point。

Exit: DRC/DFM 0件、RF/電源/layout checklist承認済み。

### H4: EVT

- [ ] current limit付きでSTM単体、ESP単体、両方の順にbring-up。
- [ ] Wi-Fi TX時3.3 V droop、EN timing、brownout、inrushを測定。
- [ ] 全modeの平均／peak／wake energyを測定。
- [ ] audio noise floorとWi-Fi混入を測定。
- [ ] 筐体・電池込みantenna pre-scan。
- [ ] 瞬断、slow ramp、更新中断、empty batteryをfault injection。

Exit: 電源margin、通信、音声、更新、目標寿命を実測で満たす。

## 6. ソフトウェア計画

### S0: 評価版固定と分離

- [ ] 現行評価ボードのrelease tag、build手順、実機smoke testを固定。
- [ ] GPIO、BSP sensor、EMW3080、STM32WB依存を一覧化。
- [ ] protocol/application logicをboard driverから分離。
- [ ] AI modelのFlash/RAM/arena/stack実測mapを保存。

### S1: STM32U575

- [ ] QII6Q用の新規CubeMX `.ioc` を作り、U585 projectへ上書きしない。
- [ ] clock、cache、SMPS、TrustZone、MDF/ADF、DMA、I2C、SPI slaveを最小起動。
- [ ] `ENERGY_SAFE/MONITOR/LEARN_WIFI/UPDATE` state machineを実装。
- [ ] Stop 2 + LPBAMを検証し、不要SRAM bankをpower-down。
- [ ] sensor store、audio、AI、NVM log、BootGuardを順に移植。

### S2: ESP32-C3

- [ ] ESP-IDF安定版を固定し、secure boot / flash encryption / NVS方針を決定。
- [ ] Wi-Fi provisioning、backoff、TLS、stream uploadを実装。
- [ ] BLE GATTは判定、health、battery、version、command中心にする。
- [ ] sleep、STM wake、load-switch自己保持、brownout recoveryを実装。
- [ ] A/B OTAとfactory recoveryを作り、4 MB上限をCIで検査。

### S3: STM-ESP protocol

```text
magic | protocol_version | type | flags | sequence | payload_length | payload | CRC32
```

- credit-based flow control、transaction ID、timeout/retry、冪等commandを実装。
- control、event、audio、log、firmware chunkをtype分離。
- version不整合時は安全modeへ入り、更新だけ許可。
- firmware chunkはoffset、length、chunk hashを持つ。
- SPI中断、両core reset、sequence欠落のfault testを作る。

16 kHz x 16 bit x monoはraw 256 kbit/s（32 kB/s）。SPIは8 MHzから開始して実測で決める。

### S4: 学習用Wi-Fi

- [ ] STM DMA audio ring → SPI → ESP queue → TCP/HTTPSの連続pipeline。
- [ ] sample counter、timestamp、drop counterを付与。
- [ ] Wi-Fi切断時は無制限bufferせずsession失敗を報告。
- [ ] PC側で欠落、重複、sample rate、電源状態をmetadata保存。
- [ ] 学習終了後はraw audioをbuild flagまたは認可commandで無効化可能にする。

### S5: 運用BLE

- [ ] STM推論結果を小さなevent recordでESPへ渡す。
- [ ] advertise-onlyとconnection方式を電力／latencyで比較。
- [ ] queue drop、重複排除、時刻同期、再送範囲を決定。
- [ ] Wi-Fi stackを初期化せず不要RF wakeを0にする。
- [ ] ESP OFFとDeep-sleepのevent latency／energyを比較。

### S6: 統合OTA

- [ ] manifestにproduct、HW、両FW version、size、hash、署名、依存versionを格納。
- [ ] ESPを互換versionへ先に更新し、その後STM inactive bankを更新。
- [ ] 更新前に蓄電量、外部電源、温度、書込みenergy reserveを確認。
- [ ] 両coreでtrial boot、health confirm、rollbackを実装。
- [ ] chunk、manifest、apply、first bootの各地点で自動電源断test。
- [ ] anti-rollbackと開発用downgrade解除を分離。

## 7. 検証matrix

| 領域 | 必須試験 |
|---|---|
| 電源 | 最小／最大入力、cold/hot、slow ramp、Wi-Fi peak、brownout、leakage |
| 音声 | 16 kHz連続、sample欠落0、RF混入、AI accuracy差分 |
| BLE | PHY/MTU/interval、混信、距離、再接続、event欠落 |
| Wi-Fi | AP/DHCP/DNS/TLS失敗、再送、長時間stream、energy上限 |
| protocol | CRC、sequence、両core reset、version mismatch、fuzz |
| OTA | 両core A/B、全段階電源断、不正署名、容量超過、rollback |
| 製造 | SWD/UART、RF、current screening、serial/key provisioning |

## 8. milestone

1. `M0 Feasibility`: 電源、無線運用、Flash、pinを確定。
2. `M1 Dual-EVK`: U575環境とC3 moduleを接続しSPI/audio/BLE/Wi-Fiを実証。
3. `M2 EVT PCB`: 測定point付き基板を外部電源で全機能確認。
4. `M3 Low-power`: gating、Stop/Deep-sleep、solar/storageを実測成立。
5. `M4 Secure OTA`: bundle更新と全電源断matrixを合格。
6. `M5 DVT`: 温度、筐体、RF、寿命、製造testを合格。

前段Exitを満たすまで次へ進まない。PCB発注前にM0、寿命宣言前にM3を必須とする。

## 9. 旧計画の統合／廃止

| 既存項目 | 扱い |
|---|---|
| sensor/audio/AI/state/log | STM application資産として移植 |
| EMW3080 Wi-Fi | ESP32-C3へ置換。driverは移植しない |
| STM32WB BLE patch | ESP-IDF BLEへ置換。wire要件だけ継承 |
| ESP32-H2 + USB CDC案 | 廃止。C3 + SPI/UARTへ置換 |
| 評価ボードOTA | STM BootGuardを継承しESP bundle managerを追加 |
| BLE raw audio | 学習時Wi-Fiへ統一。BLEは結果／health中心 |
| LC3調査 | 不採用。帯域要件変更時のみ再評価 |
| 評価ボード低優先課題 | 製品要件に影響するものだけ再登録 |

## 10. M0までの未決事項

- 電池chemistry、交換／充電式、solarと同一SKUか。
- panel寸法、実照度、無日照保証日数。
- センサー／マイク型番、周期、推論duty、event latency。
- BLE advertise-onlyか接続維持か。
- Wi-Fiは外部電源必須か、蓄電後に電池でも許可するか。
- 配布server、PKI、鍵注入、量産provisioning。
- STM imageをstream更新するか外部NORを追加するか。

未決値を推測してPMIC、storage、partition、PCBを確定しない。
