# 設計: 通信リンクの状態遷移(BLE / TCP / UART の独立ステートマシン)

> ブランチ: `refactor/layering` / 作成: 2026-07-16
> 目的: BLEの10Hzテレメトリが「一瞬止まる」問題を根治し、Phase B以降(録音)を安定動作させる。

## 背景(なぜ)

BLE 10Hz テレメトリが約5秒ごとに約300ms止まる。実測(bleak直結20秒)で
gap中央値120ms・最大240ms、5秒周期のスパイクを確認。

**根本原因**: `Service::poll()` は BLE送信 → TCP accept を**同一ループで直列実行**する。
TCPクライアント未接続時、`comm_wifi::PollRecv()` が5秒ごとに `MX_WIFI_Socket_accept()` を
呼び、これが約300msブロックする(RCVTIMEO=100ms設定だがモジュールが効かせず実測300ms)。
このブロック中 BLE の `SendStatus()` が回らず、10Hzが乱れる。

現状は `telemetryEnabled`(低電力)でしか分岐せず、**リンクごとの状態がない**ため
「BLEを使っているからTCP accept は止める」といった制御ができない。

## 設計方針(ユーザー指示)

各通信リンク(BLE / TCP / UART)を**独立したステートマシン**として持ち、
- アクティブなリンクは自分の処理を回す
- 通信が途絶える or 終了コマンドを受けたリンクは **IDLE(待機)** へ遷移し、
  そのリンクのブロッキング処理(TCP accept 等)を回さない
ことで、待機中リンクがアクティブリンクを邪魔しないようにする。

## リンク状態モデル

各リンクに共通の3状態:

```
        (初期/切断/終了cmd)
             │
             ▼
   ┌──────────────────┐   相手が現れた/接続     ┌──────────────────┐
   │  IDLE (待機)      │ ─────────────────────▶ │  ACTIVE (稼働)    │
   │  ブロッキング処理  │                        │  送受信を回す     │
   │  を回さない/低頻度 │ ◀───────────────────── │                  │
   └──────────────────┘   無通信タイムアウト/    └──────────────────┘
                          終了コマンド
```

- **UART(コンソール/VCP)**: 常時 ACTIVE でよい(DMA駆動、ブロックしない)。
  ただし状態モデルには載せ、他と一貫させる。
- **TCP**: クライアント未接続 = IDLE。IDLE中は accept を**低頻度**(現状5秒→さらに延長、
  例30秒)に間引く。クライアント接続 = ACTIVE(recvを10msで回す)。切断/終了で IDLE へ。
- **BLE**: セントラル未接続 = IDLE(notify送信しない、既存の `bleConnected` 判定)。
  接続 = ACTIVE(10Hz notify)。切断/無通信タイムアウト/終了で IDLE へ。

## 実装(最小構成・既存資産を活用)

### 新規: リンク状態の定義(comm_service 内)

```cpp
enum class LinkState : uint8_t { Idle, Active };
struct LinkFsm {
  LinkState state = LinkState::Idle;
  uint32_t lastActivityMs = 0;
};
LinkFsm bleLink_, tcpLink_, uartLink_;
```

### poll() の変更(核心)

1. **BLEリンク**: `comm_ble::IsConnected()` で ACTIVE/IDLE を更新。
   ACTIVE のときだけ `SendStatus()`(既存の未接続ガードは残す)。
2. **TCPリンク**: `comm_wifi::HasClient()` で判定。
   - ACTIVE(クライアント有): 毎poll `pollTcp()`(recv 10ms、軽い)。
   - IDLE(クライアント無): accept を**30秒に1回**に間引く。
     → これで「5秒ごと300msブロック」が「30秒ごと1回」に激減し、
     BLE 10Hz への影響が実質消える。
     さらに **BLEが ACTIVE の間は accept を完全スキップ**するオプション条件も入れる
     (BLE利用中はTCP同時利用が稀なため、10Hzを最優先)。
3. **終了コマンド**: PCから「待機へ遷移」コマンド(既存の 's'=stream stop や
   新設の終了cmd)を受けたら該当リンクを IDLE に落とす。まずは
   **無通信タイムアウト**と**接続状態**による自動遷移を実装し、明示的終了cmdは次段で追加。

### comm_wifi 側の変更

`PollRecv()` の `nextAcceptTick = now + 5000U`(5秒)を、**呼び出し側から
間引き間隔を渡せる**ようにする(例: `PollRecv(buf, len, acceptIntervalMs)`)。
あるいは新API `SetAcceptInterval(ms)` を追加し、poll() が BLE状態に応じて
30000ms(BLE ACTIVE時)/ 5000ms(通常)を切り替える。

## 段階実装(1ステップ=1コミット、実機PASSで次へ)

- **S-1**: TCP accept 間引き — IDLE時 5秒→30秒、かつ BLE ACTIVE 中はスキップ。
  最小変更で「一瞬止まる」を消す。実機で bleak 20秒測定し gap max < 150ms を確認。
- **S-2**: リンク状態を `LinkFsm` として明示化(BLE/TCP/UART)。poll() を
  「各リンクの状態を更新 → ACTIVE のリンクだけ処理」の構造にリファクタ。
  挙動は S-1 と同じだが、状態が可視化され終了cmd拡張の土台になる。
- **S-3**: 終了コマンド対応 — PCが各リンクへ「待機へ」を送れるようにし、
  受けたリンクを IDLE に落とす。BLE切断/TCP切断/無通信タイムアウトの自動遷移も整理。
- **S-4(検証)**: Phase B(録音)を実機で通し、録音転送中も他リンクが乱れないこと、
  録音がタイムアウトせず完了することを確認。

## ガードレール
- `FullStatus_t`/`MiniStatus`/frame_codec は不変。
- `Comm_*` 7ゲートウェイ・`CommBridge_*` はシグネチャ凍結。
- OTA信頼ルートに触れない。
- NSを触ったコミットのみ `NS_APP_VERSION` +1(本設計はSecureのみの見込み)。
- 各ステップ Debug構成・CubeIDEヘッドレスビルド・SWD書込・実機検証。

## 検証
- **止まり**: bleak `ble_jitter.py` で20秒測定、gap max・p99・ヒストグラムが改善
  (目標: gap max < 150ms、5秒周期スパイク消失)。
- **回帰**: TCP/UART の 50Hz テレメトリ、OTA往復、音声ストリーミングが影響を受けないこと。
- **Phase B**: BLE録音(REC_START→3秒→REC_STOP→REC_CHUNK/REC_END)が完走。
