# 設計: 通信/テレメトリの状態遷移(BLE / TCP / UART リンク + デバイスIDLE/ACTIVE)

> 更新: 2026-07-16 / ブランチ: `refactor/layering`
> このドキュメントは **実装済み**(コミット 05bb101〜8bcb3f1)の状態遷移設計を反映する。
> 未着手の後続作業は末尾「後回し」を参照。

## 背景・目的

BLE 10Hz テレメトリが約5秒ごとに約300ms「一瞬止まる」問題があった。実測で根本原因を確定:
`Service::poll()` が BLE送信と TCP accept を同一ループで直列実行し、TCPクライアント未接続時に
`MX_WIFI_Socket_accept()` が約300msブロックして BLE送信を巻き込んで止めていた。これを
状態遷移設計として根治し、あわせて周期の一定化・状態遷移ログ・PC時刻同期を導入した。

## 2つのスケジューラ(役割分担・統合しない)

- **NonSecure `App_Run` / `app_state.c`** = デバイス級の機械: IDLE/ACTIVE、LED、ToFスリープ、
  トリガー、テレメトリ周期(COMM→ACQUIRE→WAIT)。
- **Secure `Service::poll()`** = リンク級の機械: BLE/TCP/UART の排他と accept 制御。

両者は CMSE 境界の凍結ゲートウェイ越しにのみ接する。NonSecure は `Comm_GetLinkStatus()`
(bit0 BLE alive / bit1 WiFi up / bit2 BLE接続中 / bit3 TCPクライアント)でリンク状態を読む。

## デバイス状態機械(`NonSecure/Core/Src/app_state.c`)

```
        Trigger_Poll()!=NONE (COMM/LIGHT/AUDIO) -> lastActivityMs=now
                             │
  ┌──────────────┐  タイムアウト内に活動 or   ┌──────────────────────────────┐
  │ STATE_IDLE   │  リンクアクティブ          │ ACTIVE                        │
  │ 赤LED遅点滅  │ ─────────────────────────▶│ 緑LEDハートビート              │
  │ ToF停止      │                            │ COMM -> ACQUIRE -> WAIT       │
  │ 通信は低頻度 │ ◀───────────────────────── │  WAIT = 前回COMM戻り+周期      │
  └──────────────┘  now-lastActivityMs        └──────────────────────────────┘
      ▲              >= CFG_IDLE_TIMEOUT_MS
      │              かつ リンク非アクティブ
   default(不明/エラー)→ IDLE へフォールバック
```

- **状態**: `STATE_IDLE` / `STATE_ACTIVE_ACQUIRE` / `STATE_ACTIVE_COMM`。`switch` の `default:` で
  不明・エラー状態は IDLE に落とす(フォールバック)。
- **IDLEガード**: `now-lastActivityMs >= CFG_IDLE_TIMEOUT_MS`(既定3000ms、最終トリガーからの経過)
  **かつ** `Comm_GetLinkStatus()` の bit2/3 が立っていない(リンクが張られていない)ときのみ IDLE へ。
  任意の活動で ACTIVE 延長。
- **COMM→ACQUIRE→WAIT(周期一定化)**: COMM で `Comm_SendTelemetry` 送信後 `commReturnMs` を記録し、
  次回 COMM 予定を「前回の**戻り**+`CFG_COMM_PERIOD_MS`」に張る。送信後に ACQUIRE(次フレーム用
  センサー先読み)。センサー読取時間の揺らぎが次の送信時刻に影響せず、PC到達が一定周期になる。
  大遅延時はバースト回避で resync。IDLE中は従来通り低頻度送信。

## リンク状態機械(`Secure/Core/Src/comm_service.cpp`)

各リンク `LinkFsm { LinkState Idle/Active, lastActivityMs }`(`bleLink_`/`tcpLink_`/`uartLink_`)。
`poll()` 毎回更新: BLE=`comm_ble::IsConnected()`、TCP=`comm_wifi::HasClient()`、UART=受信バイト
(3秒無通信でIdleへエイジング)。

- **排他 + freeze修正**: 他のWiFi/BLEリンクがActiveの間、TCP accept ポーリング間隔を
  `comm_wifi::SetAcceptInterval()` で延長(BLE接続中は60000ms、非アクティブ時5000ms)。これで
  accept の約300msブロックがアクティブリンクを止めない。
- **UARTは常時割り込み可**: `poll()` 冒頭で無条件にコンソールバイトをドレインし `uartLink_` を
  Activeに。他リンクでゲートしない(DMA駆動の例外)。
- **終了コマンド**: `FRAME_CMD_LINK_STANDBY`(0x0D)受信で受信リンクを Idle 化(ACK返信)。次の
  inbound で再Active。

## 状態遷移ログ(`Secure/Core/Src/state_log.cpp`)

内蔵SRAMの固定長リング(64エントリ)に `{tick_ms, wall_ms, event, ret_val}` を記録。単一writer・
ロックフリー(`nsCmdRing` パターン)。**不揮発ではない**(汎用NVM無し・NORはOTA専用)。各リンク遷移・
LINK_STANDBY・BLE送信の所要ms(CommReturn)を記録。`poll()` が3秒周期で `[SLOG]` をコンソールに
ダンプ。`wall_ms` は時刻同期の offset を足した実時刻(未同期なら tick と同じ)。

## PC時刻同期(`FRAME_CMD_TIME_SYNC` 0x0E)

U585 に RTC は無い。PCが Unix epoch秒(u32 LE)を送り、firmware は
`epochOffsetMs = epochSec*1000 - HAL_GetTick()` を `state_log::SetEpochOffset()` に保存。以降
`wall_ms = offset + HAL_GetTick()`。リセットで offset は消える(再同期が必要)。PC側 `app.py` に
「時刻同期」「待機」ボタンを追加(`常時ACTIVE維持` トグルの隣、`self.transport.write` 経路)。

## ガードレール
- `Comm_*`/`CommBridge_*` 7ゲートウェイのシグネチャ不変(追加関数のみ:
  `comm_wifi::SetAcceptInterval`、`state_log::*`)。
- `FullStatus_t`(165B)/`MiniStatus`(39B)/`frame_codec` レイアウト不変。新コマンドIDは空き
  0x0D..0x7D、`frame_codec.h` と `protocol.py` に同一値。
- OTA信頼ルート(handleFrame の FW_* / boot guard)不変。
- NonSecure を触ったStepは `NS_APP_VERSION` +1(Step6→25, Step7→26)。
