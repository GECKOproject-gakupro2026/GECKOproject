# STM32U575向け音声圧縮アルゴリズム設計

## 1. 結論

STM32U575上に、可逆FLACと非可逆Opus CBRを切り替えられるencoder interfaceを実装する。
音質・AI精度・転送energyを比較する基準をFLAC、通信量を直接制御する実用候補をOpusとする。

- 共通入力: sample rate補正後のsigned PCM16、16 kHz、mono
- `FLAC_*`: 256 samples固定、可逆、内容依存の可変長
- `OPUS_CBR_*`: 320 samples／20 ms固定、非可逆、16～64 kbit/s
- 実装: fixed-point優先、static allocation、session開始時にprofileを固定
- 完全性: sequence、CRC、sample countでtransport欠落を検出
- 品質評価: 同一PCM masterから全profileを生成し、blind ABXとAI精度で比較

FLACは復号後のPCMをbit単位で元に戻せる。固定予測とRice符号は音声のsample間相関を
小さい残差へ変換するだけで、周波数帯域、量子化bit、無音、noiseを削除しない。

## 2. 現行環境から導いた制約

| 現行条件 | 設計への反映 |
|---|---|
| `CFG_AUDIO_SAMPLE_RATE = 16000` | codec入力を16 kHzに固定 |
| DMA capture 2048 samples | half-buffer 1024 samplesを4 blockに分割 |
| sample rate補正後は512 samples単位 | 1回の出力を2 blockに分割 |
| `FRAME_MAX_PAYLOAD = 1024` | 256-sample verbatimでもheader込みで余裕を確保 |
| STM32U575QII6Q: Cortex-M33、最大160 MHz、SRAM 786 KB | FPU不要の整数演算と小さなstatic work areaを採用 |
| 学習時はSTM推論を停止可能 | CPU時間をcapture、codec、SPIへ優先配分 |

「原音との一致」は、マイクのanalog波形やPDM入力ではなく、現在のpipelineがsample rateを
補正し、codecへ渡したPCM16を基準とする。補正処理自体がsample値を変更するためである。

256 samplesを選ぶ理由は、16 msの低latencyと既存frame上限への適合である。512 samplesの
verbatimはPCMだけで1024 bytesになり、codec headerやtransport metadataが入らない。

## 3. Encoderアルゴリズム

各256-sample blockを次の順で処理する。

1. 全sampleが同値ならconstant subframeを選ぶ。
2. verbatim subframeの必要bit数を暫定bestとする。
3. fixed predictor order 0、1、2について`int32_t`で残差を生成する。
4. 各orderについてRice parameter `k=0..14`の正確な符号長を計算する。
5. warm-up sample、subframe header、paddingを含め、最小bit数の候補を選ぶ。
6. fixed predictorがverbatimより短い場合だけRice符号化する。
7. それ以外はverbatimを出力する。
8. FLAC frame header、CRC-8、CRC-16を付ける。

概念コードは次のとおり。

```text
encode(block[256]):
    if all_samples_equal(block):
        return emit_constant(block[0])

    best = estimate_verbatim()
    best_order = VERBATIM
    best_k = 0

    for order in 0..2:
        residual = make_fixed_residual_i32(block, order)
        for k in 0..14:
            bits = subframe_overhead(order)
                 + warmup_bits(order)
                 + rice_bits_exact(residual, k)
            if bits < best:
                best = bits
                best_order = order
                best_k = k

    if best_order == VERBATIM:
        return emit_verbatim(block)
    return emit_fixed_rice(block, best_order, best_k)
```

signed residualは符号をfoldしてunsigned値へ写像してからRice符号化する。符号長計算と
bit writerでは、負数shiftやsigned overflowに依存しない明示的な`uint32_t`演算を使う。
order 2までならPCM16からの残差は`int32_t`に安全に収まる。

初期版ではpartition orderを0に固定する。複数partitionは音質を変えないが、探索回数と
実装複雑度を増やすためである。実録音で有意な効果が確認できた場合だけpartition order 1
（128 samples x 2）を追加する。fixed order 3、4も同じ扱いとする。

### 3.1 可変圧縮profile

可逆圧縮では、JPEGのquality値のように目標圧縮率を直接指定できない。指定できるのは
「どこまで候補を探索するか」であり、探索を増やすと平均sizeが小さくなる可能性がある一方、
CPU時間とenergyが増える。どのprofileでも復号PCMは完全に同一で、音質差は0である。

| profile | predictor探索 | Rice partition探索 | 目的 |
|---|---|---|---|
| `LOSSLESS_FAST` | order 0～1 | order 0 | 最小CPU／初期実装 |
| `LOSSLESS_BALANCED` | order 0～2 | order 0 | 標準設定 |
| `LOSSLESS_MAX` | order 0～4 | order 0～1 | 最大圧縮率の評価 |

session開始時にprofileを指定し、session途中では変更しない。metadataにはprofile ID、
encoder version、実測raw bytes、compressed bytesを保存する。`LOSSLESS_MAX`はdeadlineを
満たした場合だけ製品候補とし、満たさない場合は処理を開始せずsession開始を拒否する。
圧縮率は`1 - compressed_bytes / raw_pcm_bytes`としてsession終了後に算出する。

### 3.2 非可逆Opus profile

圧縮率を直接変える実用profileとしてOpus hard-CBRを採用する。入力FIFOへ補正後PCMを連続して
積み、320 samplesごとに20 ms frameをencodeする。既存の512-sample処理境界とは一致しないため、
frameごとにencoderをrestartせず、FIFOとcodec stateをsession全体で維持する。

| profile | bitrate | 20 ms packet | raw PCM比の削減率（codec payloadのみ） |
|---|---:|---:|---:|
| `FLAC_BALANCED` | 内容依存 | 可変 | 内容依存、劣化0 |
| `OPUS_CBR_64K` | 64 kbit/s | 160 bytes | 75% |
| `OPUS_CBR_48K` | 48 kbit/s | 120 bytes | 81.25% |
| `OPUS_CBR_32K` | 32 kbit/s | 80 bytes | 87.5% |
| `OPUS_CBR_24K` | 24 kbit/s | 60 bytes | 90.625% |
| `OPUS_CBR_16K` | 16 kbit/s | 40 bytes | 93.75% |

表の削減率はraw 256 kbit/sとの比較で、12-byte transport headerを各20 ms frameへ付ける
場合の実効削減率は約73.1、79.4、85.6、88.8、91.9%となる。複数frameを1 transport packetへ
まとめればheader比率を下げられる。

初期設定は`OPUS_CBR_32K`、20 ms、mono、`OPUS_APPLICATION_AUDIO`、complexity 3とする。
bitrate以外を固定して音質差を比較する。STM実測でdeadlineを満たさない場合はcomplexityを
2、1、0の順に下げる。DTXは区間ごとに実効圧縮率が変わり比較を曖昧にするため初期評価では
無効とする。profileはsession開始時だけ変更でき、途中変更は禁止する。

### 3.3 音質・AI精度の比較

録音条件の差を混ぜないため、`FLAC_BALANCED`で可逆masterを1回取得し、同じPCMから全Opus
profileを生成する。実機encoderとPC reference encoderの両方を同じ設定で比較する。

比較用fileはすべて16 kHz、mono、PCM16へdecodeし、同じloudness、sample数、開始位置に揃える。
file名からcodec／bitrateを隠してrandom化し、ABXまたは二重盲検で聞き比べる。評価項目は
音声明瞭度、子音、環境音、瞬間音、metallic artifact、noiseの変化、総合的な違和感とする。

非可逆音声も学習datasetに採用可能とするが、metadataへcodec、bitrate、complexity、encoder
versionを必ず記録する。各profileについて人の聴感だけでなく、可逆referenceとのmacro-F1、
class別recall、false positive率を比較する。可逆masterは再評価用に保持する。

## 4. Bufferとtransport

1 block当たりのencoder出力領域は640 bytesを予約する。verbatimの512 bytesとFLAC header、
CRC、byte alignmentを収容し、既存の1024-byte payload上限を超えない。

新しいaudio transport payloadは次の論理構造とする。

| field | size | 内容 |
|---|---:|---|
| block index | 4 bytes | session内の単調増加番号 |
| first sample index | 4 bytes | 欠落・重複検出 |
| codec packet length | 2 bytes | 可変長packetの長さ |
| flags | 2 bytes | session開始／終了／error |
| codec packet | 最大640 bytes | FLAC frameまたはOpus packet |

8-bitの既存sequenceだけでは数秒で周回するため、audio payloadには32-bit indexを追加する。
STMはcodec packetを生成し、ESP32-C3はdecode／再encodeせずopaque dataとしてTCP/HTTPSへ
転送する。PC側assemblerがsession metadataとframe列から最終`.flac`を構築し、総sample数
など確定後のmetadataを完成させる。

推奨static memory budgetは次のとおり。

| 用途 | 量 |
|---|---:|
| 入力block | 512 bytes |
| residual scratch | 1024 bytes |
| encoder出力 | 640 bytes |
| 16-block ring（256 ms） | 10240 bytes |
| index、bit writer、hash state等 | 1 KB未満 |
| 追加SRAM合計目安 | 約13 KB |

実装時はTrustZoneのSecure／Non-Secure SRAM配置とstack high-water markを再計測する。
heap allocationは使わない。

## 5. Schedulingと電力

DMA half-buffer 1024 samplesは64 msごとに到着する。FLACでは4 block、OpusではFIFO上の
3または4 frameをその間に処理する。
初期合格値を次のように置く。

- 1024 input samples分のencode時間: 6.4 ms未満（64 ms周期の10%未満）
- capture overrun: 0
- compressed ring overflow: 0
- encoder taskのheap allocation: 0
- 最悪入力時も平均供給rate: raw相当32 kB/s + transport overhead以上

学習用`LEARN_WIFI` modeではAI推論、BLE advertising、不要なsensor telemetryを止め、
capture、encode、SPI、Wi-Fiに処理と電力を集中する。ESP側は複数blockをまとめてsocketへ
書き込み、Wi-Fi radioの起床回数を減らす。ただし待ち時間に上限を設け、ringを溢れさせない。

可逆圧縮では、すでにentropyが高いnoiseを必ず小さくすることはできない。この場合も
verbatim subframeに切り替えるため情報は失わないが、転送量はraw相当になる。したがって
電池寿命の見積りは平均圧縮率だけでなく、圧縮率1.0のworst caseでも行う。

## 6. 完全性

完全性をcodec、transport、sessionの3層で検証する。

1. FLAC frameのCRC-8／CRC-16でcodec frame破損を検出する。
2. transport CRCと32-bit block/sample indexで破損、欠落、重複、並び替えを検出する。
3. STM32 HASH acceleratorでcodec入力PCMと送信codec packetのSHA-256を逐次計算する。
4. FLACではPC側復号PCMのSHA-256とsample数を計算し、入力PCMと照合する。
5. Opusでは受信codec packetのSHA-256を送信packetと照合し、非可逆変換とは別にtransport
   破損がないことを保証する。

PCM hashのbyte orderを`PCM16 little-endian`に固定する。hash不一致、欠落、CRC error、
ring overflow、Wi-Fi切断のいずれかが発生したsessionは学習datasetへ自動登録しない。

## 7. 実装順序

1. PC上に同じ限定encoderとRFC準拠decoderを用いたtest harnessを作る。
2. constant、impulse、ramp、最大／最小値交互、white noise、実録音でround-tripを試験する。
3. STMにFLAC encoderを移植し、既存の補正後512-sample出力を256 x 2へ分割する。
4. Opus fixed-point encoderと320-sample FIFOを追加し、bitrate/profile commandを実装する。
5. 連続DMA下でcycle count、SRAM、ring occupancy、dropを記録する。
6. ESPのopaque forwardingとPC assemblerを実装する。
7. 電源測定でFLACと全Opus bitrateを比較する。
8. blind ABXとprofile別AI精度から標準bitrateを決定する。

## 8. 採用試験

- すべてのtest vectorでsource/decode PCMのSHA-256とsample数が一致する。
- 8時間連続captureでDMA overrun、block欠落、重複、CRC errorが0。
- white noiseでverbatim fallbackし、buffer overflowせず送信を継続する。
- 電源断、ESP reset、STM reset、Wi-Fi再接続後に壊れたsessionが正常sessionとして扱われない。
- reference FLAC decoderでPC側生成物を復号できる。
- reference Opus decoderで全CBR profileを復号でき、packet sizeが設定値と一致する。
- bitrateごとにblind ABX結果とAI精度差を記録し、採用根拠を残す。
- 実録音について圧縮率、STM encode energy、ESP Wi-Fi energy、session総energyを記録する。
