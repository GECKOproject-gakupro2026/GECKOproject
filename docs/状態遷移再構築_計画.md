## Context(なぜこの変更をするか)

ユーザー報告の2つの実問題:

1. **IDLE状態なのにセンサーデータが5Hzで送られてくる**(ToFだけ値が来ない)。
2. **センサーのサンプリングレートが遅く、データが滑らかでない**。

### 原因(コードで確定済み)

**問題1**は仕様通りの実装で、要求と食い違っている。[app_state.c:156-168](../NonSecure/Core/Src/app_state.c#L156-L168):

```c
if (ctx->state == STATE_IDLE) {
  if ((int32_t)(now_ms - ctx->nextTelemetryMs) >= 0) {
    ctx->nextTelemetryMs = now_ms + CFG_IDLE_TELEMETRY_MS;  /* 200ms = 5Hz */
    build_status(&ctx->st);              /* ← IDLEなのに全センサー取得 */
    (void)Comm_SendTelemetry(&ctx->st);  /* ← IDLEなのに送信 */
  }
  ...
}
```

[app_config.h:24-26](../NonSecure/Core/Inc/app_config.h#L24-L26) にも
「*IDLE no longer silences the comm stack — only the slower rate distinguishes it from ACTIVE*」
と明記されている。これは過去のIDLE再定義(「通信を止めるとIDLE復帰不能になるので止めない」)の
名残であり、現在の要求と矛盾する。**ToFだけ値が来ない**のは `Sensors_Stop()` がIDLE突入時に
ToFをSLEEPさせ `s_tofOk=0` にし、[sensors.c:170-177](../NonSecure/Core/Src/sensors.c#L170-L177)
が `tof_ok=0, tof_mm=0` を返すため。つまり「ToF以外は全部動いていてIDLEで5Hz送信され続け、
ToFだけ止まる」という観測通りの挙動。

**問題2**は送信レート(50Hz)とセンサー取得レートの乖離。取得はセンサーごとに個別周期で動く:

| データ | 現在の取得周期 | レート | ハード制約 |
|---|---|---|---|
| 加速度・ジャイロ・地磁気 | 毎回(周期なし) | 送信レート依存(50Hz) | ODR 208/208/100Hz設定済み |
| 温湿度・気圧 | 100ms | 10 Hz | ODR 12.5Hz(=80ms)/75Hz |
| 照度 | 200ms | 5 Hz | 積分時間 |
| ToF距離 | 500ms | 2 Hz | I2C 約35ms/read、profile Frequency=5Hz/TimingBudget=30ms |
| MCU情報 | 500ms(Secure側) | 2 Hz | — |

50Hzで送信しても中身は10Hz/5Hz/2Hzでしか更新されないため、同じ値が5〜25回繰り返される。

### 要求する構造(memo.md:78-100)

> **idle**: uartのdmaや各種フラグ、またはwifi BLEからのコマンドを待機している状態。それ以外の動作はしない
> **データ送信**: メモリに保存されているデータを送信する
> **データ取得**: センサーデータを取得する。センサー周期以上のデータ取得を要求する可能性がある。センサー周期はコマンド上で指定できる機構を追加すること
> **データ保存領域**: 構造体を用いてクラス化し、プロジェクト全体で共有する。データ取得では上書きし、データ送信では送信する

**状態遷移を正しく構造化すれば両問題とも構造的に解決する**(取得と送信が分離され、IDLEでは
どちらも起きない)。

### ユーザーの確定した設計判断(要確認事項への回答)

- **IDLE中**: センサーデータ取得も送信もしない。ただし「**IDLE状態であることを示す軽量コマンド**」
  (新規 `FRAME_CMD_IDLE_BEACON`)を低頻度(1Hz)で送る → app.pyは「生きているがIDLE」と分かる。
- **照度と音圧は例外**: IDLE中もこの2つだけは取得してよい。これにより `Trigger_Poll()` の
  照度/音圧トリガー(=ファームがフラグを立てて状態遷移する経路、memo.md:51-53)がIDLE中も
  生き続ける。**取得はするが送信はしない**(トリガー判定専用)。
- **センサー周期指定**: **センサー種別ごとに個別指定**(env/light/tof/motion)。
- **優先度**: 本計画が最優先(既存の未解決項目 D1/E より先)。

### 設計判断: 共有データ構造の「クラス化」

要求「センサーデータの保存は構造体を用いてクラス化し、プロジェクト全体で共有する」について、
**`FullStatus_t`(165B、`comm_dto.h`)は165Bレイアウト凍結のため構造体自体は変更できない**
(ガードレール)。代わりに **`sensor_store.h/.c` を新設**し、`FullStatus_t` の**単一インスタンスを
このモジュールが所有**する。`app_state.c` は `ctx->st` を直接触らず、このAPI経由でのみ
アクセスする(取得=上書き、送信=読み出し)。これが要求の「クラス化して共有」の実体。

### ⚠️ 最重要リスク: IDLE復帰不能事故の再発

過去に「**IDLE中に通信を止めたらIDLE復帰不能(吸収状態)になった**」事故がある。本計画は
まさに「IDLE中にデータ送信を止める」変更なので、同じ轍を踏む危険がある。

**再発防止の根拠**: 現在は復帰経路が `Comm_TakeExplicitWake()`(UART DMA駆動の明示コマンド
`FRAME_CMD_ENTER_COMM`=0x0F)に作り直され、`Comm_Poll()` は `App_Run` で**毎周無条件に呼ばれ続ける**
([app_loop.c:44](../NonSecure/Core/Src/app_loop.c#L44))ので、送信を止めても**受信は生き続ける**。

**各Stepの必須検証**: IDLEに落としてから `ENTER_COMM` 1発で復帰することを**連続5回**確認する。
1回でも失敗したら即ロールバック(`git reset --hard HEAD`)し、原因を特定してから再開する。

## Step 1: `sensor_store` を新設し、取得と送信の境界を作る(挙動不変)

- **目的**: `FullStatus_t` の単一所有者を作り、以降のStepで「取得」と「送信」を分離できる土台にする。
  このStepでは**挙動を変えない**(リファクタのみ)。
- **新規**: `NonSecure/Core/Inc/sensor_store.h`, `NonSecure/Core/Src/sensor_store.c`。
- **API骨格**(`FullStatus_t` のレイアウトは触らない。所有権だけを移す):
```c
/* センサーデータの単一保管庫。プロジェクト全体でこのインスタンスのみを共有する。
 * 取得(AcquireXxx)で上書きし、送信側は GetForSend() で読むだけ。 */
void                SensorStore_Init(void);
/* データ取得状態: 全センサーを読んで保管庫を上書きする(env/motion/tof/light/audio/MCU)。 */
void                SensorStore_AcquireAll(void);
/* IDLE用の例外取得: トリガー判定に要る照度と音圧だけを更新する。 */
void                SensorStore_AcquireTriggerInputs(void);
/* データ送信状態: 保管庫の現在値を読む(取得はしない)。 */
const FullStatus_t *SensorStore_GetForSend(void);
/* Trigger_Poll() に渡す用(読み取り専用の同一インスタンス)。 */
const FullStatus_t *SensorStore_Peek(void);
```
- **変更**: `NonSecure/Core/Src/app_state.c` の `build_status()` を `sensor_store.c` へ移し
  (`SensorStore_AcquireAll` の実体にする)、`AppStateCtx_t.st` を削除して `sensor_store` 経由に
  差し替える。`Trigger_Poll(&ctx->st)` → `Trigger_Poll(SensorStore_Peek())` に。
  `NonSecure/Core/Inc/app_state.h` から `FullStatus_t st;` メンバを削除。
- **注意**: `Comm_SendTelemetry()` は `const FullStatus_t *` を取るのでそのまま渡せる。
  ガードレールにより `Comm_*` のシグネチャは変えない。
- **ビルド**: NonSecure。`NS_APP_VERSION` を **30** に。
- **検証(PASS)**: `python pc_side/status_monitor/app.py` をターミナルで起動しUART接続。
  **挙動が変わっていないこと**を確認: ACTIVE時 約50fps、IDLE時 約5fps(このStepではIDLE送信は
  まだ残っている)、CRCエラー0。IDLE→`ENTER_COMM`で復帰を**5回連続**成功。
- **コミット**: `refactor(ns): give FullStatus a single owner in sensor_store (no behaviour change)`

## Step 2: IDLEでは取得も送信もしない + IDLE_BEACONを送る

- **目的**: 要求の中核。**問題1を根治**する。
- **新規コマンド**: `FRAME_CMD_IDLE_BEACON = 0x14`。
  - `Secure/Core/Inc/frame_codec.h` と `pc_side/status_monitor/protocol.py` に
    **同一値・同一コミット**で追加(不一致は無言の通信断)。
  - payload: `[uptime_ms u32 LE][device_state u8]`(5B)。センサー値は載せない。
- **変更**: `NonSecure/Core/Src/app_state.c` のIDLEブロック(現156-168行)を書き換える:
```c
if (ctx->state == STATE_IDLE)
{
  /* 要求: IDLEでは「uartのdma/フラグ/BLE・WiFiコマンドを待機」する以外の動作をしない。
   * 例外として照度・音圧だけは取得する - Trigger_Poll() の TRIG_LIGHT/TRIG_AUDIO
   * (=ファームウェア自身がフラグを立てて状態遷移する経路)がIDLE中も生きるように。
   * 取得はするが送信はしない(トリガー判定専用)。 */
  SensorStore_AcquireTriggerInputs();

  /* データではなく「IDLEで生存中」だけを低頻度で知らせる。 */
  if ((int32_t)(now_ms - ctx->nextBeaconMs) >= 0)
  {
    ctx->nextBeaconMs = now_ms + CFG_IDLE_BEACON_MS;
    Comm_SendIdleBeacon((uint32_t)ctx->state);
  }
  ctx->haveAcquired = 0U;
  return;
}
```
- **新規NSCゲートウェイ** `void Comm_SendIdleBeacon(uint32_t state)`(既存7つは不変、追加は可):
  4ファイル対で追加 — `NonSecure/Core/Inc/comm_api.h` / `Secure/Core/Src/secure_nsc.c`
  (`CMSE_NS_ENTRY`、スカラー引数のみなので `cmse_check_address_range` は不要) /
  `Secure/Core/Inc/comm_backend.h` / `Secure/Core/Src/comm_service.cpp`
  (`CommBridge_SendIdleBeacon` 実体。既存 `CommBridge_TakeExplicitWake`
  [comm_service.cpp:1098](../Secure/Core/Src/comm_service.cpp#L1098) と同じ書式)。
  実体は `Frame_Encode(FRAME_CMD_IDLE_BEACON, ...)` して `comm_uart::SendAsync` +
  `comm_wifi::SendRaw`(既存 `sendUart`/`sendTcp` と同じ経路)。
- **設定追加**: `NonSecure/Core/Inc/app_config.h` に `CFG_IDLE_BEACON_MS = 1000U`(1Hz)。
  `CFG_IDLE_TELEMETRY_MS` は**用済みなので削除**(コメントも要求に合わせて書き換える)。
  `AppStateCtx_t` に `uint32_t nextBeaconMs;` を追加、`nextTelemetryMs` は削除。
- **app.py**: `_poll_queue`(現709-719行付近)の `decode_status` 呼び出し**より前**に
  `CMD_IDLE_BEACON` 分岐を追加(既存 `CMD_LOG_RESP`/`CMD_ACK` 分岐と同じ位置・書式)。
  受信したら状態ラベルを "IDLE(待機中)" に更新し、`_log` に出す。**センサー値は更新しない**
  (IDLE中は値が古いままであることがUI上も分かるようにする)。
- **ビルド**: Secure + NonSecure。`NS_APP_VERSION` を **31** に。
- **検証(PASS)**:
  1. app.pyでUART接続 → ACTIVE時 約50fps。
  2. 3秒無操作でIDLEへ → **センサーデータ(fps)が0になり**、代わりにIDLE_BEACONが約1Hzで
     届き、状態ラベルが "IDLE" になること。赤LED遅点滅。
  3. **`ENTER_COMM` 1発で確実にACTIVE復帰することを連続5回**(最重要 — 1回でも失敗したら
     即 `git reset --hard HEAD` でロールバック)。
  4. `overrun=0` が続くこと(`[PROF]`)。
- **コミット**: `feat(app): idle stops all sensing and telemetry, beacons its state instead`

## Step 3: センサー周期をコマンドで指定できるようにする

- **目的**: 要求「センサー周期はコマンド上で指定できる機構を追加すること」。**問題2への主対応**。
- **新規コマンド**: `FRAME_CMD_SET_SENSOR_RATE = 0x15`、payload `[sensor_id u8][period_ms u16 LE]`。
  `frame_codec.h` と `protocol.py` に同一追加。`sensor_id`: `0=env, 1=light, 2=tof, 3=motion`。
- **`sensors.h` に追加**: `void Sensors_SetPeriod(uint8_t sensor_id, uint16_t period_ms);`
  `sensors.c` の `SENSORS_ENV_PERIOD_MS`/`SENSORS_LIGHT_PERIOD_MS`/`SENSORS_TOF_PERIOD_MS`
  の `#define` を **static変数化**(`s_envPeriodMs=100, s_lightPeriodMs=200, s_tofPeriodMs=500`)し、
  motion用に `s_motionPeriodMs = 0`(**0 = 毎回読む=制限なし**、現状の挙動)を追加して
  `Sensors_Refresh()` のmotionブロックにも周期判定を入れる。
- **⚠️ 下限クランプ(必須)**: ハード制約を割ると I2C がループを圧迫し、Phase Aで解消した
  停止クラスの問題を再発させる。`Sensors_SetPeriod` 内で下限にクランプする:
  - `env`: 最小 **80ms**(ODR 12.5Hz の物理下限)
  - `light`: 最小 **100ms**(積分時間)
  - `tof`: 最小 **50ms**(I2C 約35ms/read。これ未満はループを食い潰す)
  - `motion`: 最小 **0**(0は「毎回」の意味。ODR 208Hz なので実質 5ms 相当が物理下限)
  - 上限は一律 **60000ms**。クランプしたら `printf("[SENS] period clamped ...")` で残す。
- **Secure→NonSecure 伝達**: 新規NSCゲートウェイ
  `uint32_t Comm_TakeSensorRateCmd(uint8_t *sensorId, uint16_t *periodMs);`
  (戻り値: 1=取得した/0=なし。**既存 `Comm_TakeExplicitWake` と同じ「一回消費」パターン**)。
  4ファイル対で追加。Secure側は `handleFrame` の `FRAME_CMD_SET_SENSOR_RATE` case で
  `pendingSensorRate{id, period, valid}` に積み(既存 `explicitWakeRequested`
  [comm_service.cpp:99](../Secure/Core/Src/comm_service.cpp#L99) と同じ file-scope volatile
  パターン)、ACKを返す(既存 `FRAME_CMD_ENTER_COMM` case
  [comm_service.cpp:466](../Secure/Core/Src/comm_service.cpp#L466) が実例)。
  **ポインタ引数があるので `secure_nsc.c` 側で `cmse_check_address_range(..., CMSE_NONSECURE|CMSE_MPU_READWRITE)`
  検証 + Secureローカルコピーが必須**(既存 `Comm_GetMcuInfo` が実例)。
- **NonSecure側で消費**: `AppState_Tick` の冒頭(Trigger_Poll の前)で
  `uint8_t id; uint16_t p; if (Comm_TakeSensorRateCmd(&id, &p)) Sensors_SetPeriod(id, p);`
- **app.py**: センサー周期設定UI(4センサー分のスピンボックス+適用ボタン)。送信は既存
  `_sync_time`/`_send_standby` と同じ `self.transport.write(protocol.build_frame(...))` パターン。
- **ビルド**: Secure + NonSecure。`NS_APP_VERSION` を **32** に。
- **検証(PASS)**:
  1. app.pyから `tof=200ms` を送る → ACK受信。全データタブでToFの値が**2Hzから5Hzに増える**
     (値の変化頻度で判断)。
  2. `env=80ms` を送る → 温湿度の更新が 10Hz→12.5Hz 相当に。
  3. **下限クランプ確認**: `tof=10ms` を送る → `[SENS] period clamped` が出て 50ms に留まり、
     **50fpsのUARTテレメトリが乱れないこと**(ここが崩れるとループ圧迫の再発)。
  4. `ENTER_COMM` でのIDLE復帰が引き続き5回連続成功。
- **コミット**: `feat(sensors): per-sensor acquisition period settable at runtime by command`

## Step 4(任意): ToF profile を上げて実効レートを稼ぐ

- **目的**: Step 3で `tof` 周期を短くしても、**センサー側の profile が 5Hz/TimingBudget=30ms
  なので実効レートは上がらない**。ここを詰める。
- **対象**: `NonSecure/Core/Src/sensors.c` の `tofInitAndStart()`(現38-43行):
  `profile.RangingProfile = RS_PROFILE_4x4_CONTINUOUS; profile.TimingBudget = 30; profile.Frequency = 5;`
- **変更**: `Frequency` を 5→10Hz程度に上げ、`TimingBudget` を実測しながら詰める
  (4x4なら TimingBudget を下げても精度への影響は限定的)。**上げすぎるとI2C時間がループを
  圧迫する**ので、`[PROF]` の loops/s と 50Hz テレメトリが崩れない範囲に留める。
- **検証(PASS)**: ToF更新が実測で 5Hz以上、かつ UART 50fps・`overrun=0` が維持されること。
- **コミット**: `perf(sensors): raise the ToF ranging profile to match the faster poll period`

## 検証方法(エンドツーエンド)

- **app.pyを実際にターミナルで起動**して観察する(`python pc_side/status_monitor/app.py`)。
- **ACTIVE**: 約50fps、CRC0、緑LEDハートビート。
- **IDLE**: **センサーfps=0**、IDLE_BEACONが約1Hz、状態ラベル "IDLE"、赤LED遅点滅。
- **復帰**: `ENTER_COMM` 1発で即ACTIVE(5回連続)。
- **周期変更**: 各センサーの更新頻度が指定通りに変わる。下限クランプが効く。
- **回帰**: 音声ストリーミング(`a`/`s`)、BLE録音、OTA往復が壊れていないこと
  (BLE/OTAはStep2完了後に1回まとめて確認でよい)。
