## 未着手・要判断

### 1. BLE録音チャンクの稀な無線層欠落(仕様として受容、対策は保留)

- **背景**: BLE録音の連続ストリーミング転送は実機で安定動作(60〜90秒録音で欠落0%、
  DMA取りこぼし0)。ただし3分録音では BLE 無線層(notify = Write Without Response 相当)
  の取りこぼしにより 0.07%(2ブロック=59msの単発音飛び×2)が発生した。ボード側の
  リング/送信/テレメトリ停止・DMAキャプチャは全て正常で、これは無線層固有の稀な欠落。
- **やること(対策する場合)**: 選択肢は(a)PC側で欠落seqを前後ブロックで補間して音飛びを
  目立たなくする、(b)ボード側にREC_RESEND(欠落ブロック再送)を実装する
  (ただし送信済みブロックはリングから解放されるため、再送にはリング保持期間の延長が必要で
  実装コスト大)。ユーザー判断で「0.07%は実用上問題ない」として現状維持を選択済み。
- **優先度**: 低(ユーザー承認により現状維持。音飛びが問題化した場合のみ着手)。

### 2. TCP accept が IDLE 状態限定であることの運用上の制約

- **背景**: TCPの新規接続 accept は「未接続 かつ IDLE(deviceState==0)」のときだけ行う
  (ノークライアント時の accept が ~300ms ブロックし、ACTIVE中の poll() ループを圧迫する
  ため。特にBLE録音の連続ストリーミング転送で問題になる)。接続済みクライアントの受信
  (recv)は ACTIVE 中も継続する(`f4be445` で修正)。
- **制約**: 新規に WiFi/TCP 接続や OTA を始めたいとき、ボードが ACTIVE
  (BLE接続中・UART通信中・録音中など)だと accept されず接続できない。ボードが IDLE に
  落ちる(無通信 `CFG_IDLE_TIMEOUT_MS`=3秒)のを待つ必要がある。実機では
  「リセット直後は起動時ACTIVE→3秒でIDLE→accept可能」という順序。
- **やること(改善する場合)**: 例えば「TCP listen ソケットがあり未接続なら、ACTIVE中でも
  低頻度(数秒に1回)で1回だけ accept を試す」など、accept ブロックの影響を抑えつつ
  ACTIVE中の新規接続も受けられる設計を検討する。ただし現状はIDLE経由で接続できるので
  致命的ではない。
- **優先度**: 低〜中(実用上は接続前にボードをIDLEにすれば回避できる。UXの改善余地)。

### 3. LC3代替案の実測(調査のみ完了、実装は保留)

- **背景**: `docs/LC3導入_実現性調査.md` §5で「LE Audioスタックを使わずU585側でLC3を
  ソフトエンコードし既存GATT notify経路で送る」代替案を検討したが、CPU負荷・音質差とも
  未検証のまま「動機が薄いので着手保留」と結論した。
- **やること(着手する場合)**: まずCPU負荷の実測(既存の音声パイプラインへの割り込み具合)
  から始める。ライブラリ選定(`google/liblc3`等)、`recorder.hpp`/`audio_capture.cpp`の
  エンコードパス差し替え、PC側デコーダ追加が必要。
- **優先度**: 低(ユーザー判断待ち。音質向上の具体的な要求が出てから着手が妥当)。

### 4. VEML3235(照度センサー)5Hz制約の根本原因(未調査、深追いしない方針で確定済み)

- **背景**: §3で照度センサーの積分時間(IT)をIT100に正しく設定しても、実測の値更新周期が
  約200ms(5Hz)から短縮できなかった。ユーザー承認により「5Hzを実測上限として受け入れる」
  ことで決着済み。
- **やること**: 深追いしない方針が既に確定しているため、対応不要。もし将来的に照度の
  応答速度が問題になった場合のみ、VEML3235データシートで内部測定サイクルの制約を
  精査する(IT設定以外に測定周期を左右するレジスタが無いか)。
- **優先度**: 対応不要(方針確定済み、参考記録として残すのみ)。
