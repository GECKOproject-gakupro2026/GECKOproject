## 未着手・要判断

### 1. WiFi/TCP経路の完全な回帰確認(未実施)

- **背景**: 旧計画書の各Step検証はすべて「WiFiホットスポット未設定」という環境制約により
  UART(COM9)経由でのみ実施し、TCP依存の検証は意図的にスキップしてきた
  (`docs/refactoring/verify_regression.py` のWiFi/TCP項目は未実行のまま)。
- **やること**: `pc_side/wifi_hotspot.ps1 -Action start` でホットスポットを立ててから
  ボードをリセットし、`[TLM] Wi-Fi connected, IP=...` を確認したうえで
  `docs/refactoring/verify_regression.py` を全項目PASSまで流す。
  これまでに入った変更(IDLE_BEACON、センサー周期コマンド、BLE STATUS_FRAG、
  nvm_logのNORヘッダ方式・3B圧縮、LOG_REQ応答の6Bレコード形式)がTCP経路でも
  壊れていないことの確認。特に `LOG_REQ`/`LOG_RESP` はレコード形式が
  13B→6B に変わっている(`protocol.py` の `LOG_RECORD_FMT="<IBB"`)ので、
  TCP経由でもログ取得が正しくデコードできるか要確認。
- **優先度**: 中(UART経由では全て検証済みのため、致命的な破綻がある可能性は低いが、
  TCP固有の経路(`comm_wifi.cpp`)は未検証のまま)。

### 2. BLE `SendStatusFrag` のCPU/UART負荷実測(未実施)

- **背景**: §7-3で実装したBLE全センサーフラグメント送信(`FRAME_CMD_STATUS_FRAG`)は
  1Hzで1フラグメントずつ送る設計で、機能検証(再構成が正しく行われる)は完了しているが、
  「50Hz UARTテレメトリや`[PROF]`のloops/sを圧迫しないか」の専用実測はしていない
  (§7-3の検証時点では51.7fps・CRC0で問題なかったが、これは短時間の観測であり、
  録音転送やSTATUS_FRAGが同時に走る条件は未検証)。
- **やること**: 録音送信中(`IsRecTxActive()`)以外の通常運用を長時間(数分〜)観測し、
  `[PROF]` のloops/sとUART fpsが安定していることを確認する。
- **優先度**: 低(現状の実測で問題の兆候は無い)。

### 3. LC3代替案の実測(調査のみ完了、実装は保留)

- **背景**: `docs/LC3導入_実現性調査.md` §5で「LE Audioスタックを使わずU585側でLC3を
  ソフトエンコードし既存GATT notify経路で送る」代替案を検討したが、CPU負荷・音質差とも
  未検証のまま「動機が薄いので着手保留」と結論した。
- **やること(着手する場合)**: まずCPU負荷の実測(既存の音声パイプラインへの割り込み具合)
  から始める。ライブラリ選定(`google/liblc3`等)、`recorder.hpp`/`audio_capture.cpp`の
  エンコードパス差し替え、PC側デコーダ追加が必要。
- **優先度**: 低(ユーザー判断待ち。音質向上の具体的な要求が出てから着手が妥当)。

### 4. VEML3235(照度センサー)5Hz制約の根本原因(未調査、深追いしない方針で確定済み)

- **背景**: §3で照度センサーの積分時間(IT)をIT100に正しく設定しても、実測の値更新周期が
  約200ms(5Hz)から短縮できなかった。ユーザー承認により「5Hzを実測上限として受け入れる」
  ことで決着済み。
- **やること**: 深追いしない方針が既に確定しているため、対応不要。もし将来的に照度の
  応答速度が問題になった場合のみ、VEML3235データシートで内部測定サイクルの制約を
  精査する(IT設定以外に測定周期を左右するレジスタが無いか)。
- **優先度**: 対応不要(方針確定済み、参考記録として残すのみ)。
